## Why

当前项目事实信息同时存在“根目录聚合 Markdown”“三层结构说明”“JSON 化事实库”等多种表达方式，用户难以判断哪一套才是权威来源，也难以在日常协作中持续维护。产品、研发在模块定义、功能补充、API 录入、后续调整的过程中，需要一套以自然语言名称为主、低维护成本、可逐步完善且能被 Agent 稳定理解的唯一标准。

## What Changes

- **BREAKING** 将项目事实信息的权威维护方式统一为“模块档案式知识库”，以模块为唯一人工维护单元，不再要求用户手工维护机器可读 ID、跨文件交叉引用和多套并行结构。
- 规定每个模块档案使用固定骨架维护模块描述、功能点、API 清单、页面原型、包/类、依赖模块等信息，并允许随着产品与研发工作流逐步补充。
- 引入“人工维护层 + 系统派生层”模型：用户维护自然语言内容，系统自动派生内部标识、索引、关联关系和 Agent 读取视图。
- 定义以 Markdown 模块档案为权威源、并支持 Excel 导入收敛到模块档案的维护规则，确保单一事实源。
- 调整 Agent 的事实加载约定，使其优先读取模块档案及其派生索引，而不是依赖用户显式书写模块 ID 标签。
- 在项目事实信息管理模块中提供已维护事实信息的浏览能力，使用户能够查看当前已沉淀的模块、功能点、API、页面原型和包/类信息。
- 支持原型文件集中存放的模式，兼容 Axure 导出的整套 HTML 原型包；模块档案中只需手工维护关联页面名称，不要求将原型 HTML 按模块物理拆分。

## Capabilities

### New Capabilities
- `project-fact-maintenance-model`: 定义模块档案式知识库、派生索引、自动关联和多入口收敛的统一维护模型。

### Modified Capabilities
- `project-fact-information`: 将现有以 `modules.md` 为中心的星形结构，调整为以模块档案为权威事实源、以系统派生索引为 Agent 检索入口的结构。
- `structured-context-loading`: 调整事实信息加载逻辑，使 Agent 能从模块档案和派生索引中加载模块、功能、接口、类包、页面原型等上下文。
- `module-entity-resolution`: 调整模块定位方式，使系统优先基于自然语言模块名、别名和派生索引解析模块，而不是要求用户输入显式模块 ID。
- `web-ui`: 在项目事实信息管理页面展示已维护事实信息，并以模块档案视角浏览模块详情和关联信息。

## Impact

- 受影响范围包括 `project-facts/` 目录规范、事实信息导入/导出流程、上下文加载器、事实查询工具及项目事实信息管理页面的浏览体验。
- 原型文件的存放约定和模块到原型页的关联方式也将随之调整。
- 现有 `project-facts/modules.md`、`usecases.md`、`interfaces.md` 等聚合文件将需要迁移或退化为派生视图。
- 现有依赖模块 ID 标签过滤事实信息的读取逻辑需要重构，以支持按模块档案和系统索引解析关系。
