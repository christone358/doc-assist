## Context

当前项目事实信息存在三类并行表达：根目录聚合 Markdown、说明文档中的三层目录设计、以及新增的结构化 JSON 导入产物。它们分别适合 Agent 读取、人工说明和批量加工，但没有唯一事实源，导致用户难以判断应维护哪一层，也让后续导入、UI 编辑、Agent 加载很容易出现偏差。

这次变更的核心约束不是“理论上最完整的数据模型”，而是“在产品和研发的日常工作流中可持续维护”。真实维护顺序通常是：产品经理先新建模块并补充功能描述和功能点，随后研发补充 API、包/类，后续双方继续增量更新。因此设计必须允许信息不完整、逐步丰富，并避免要求用户显式维护机器可读 ID、跨文件引用和多处重复录入。

## Goals / Non-Goals

**Goals:**
- 建立唯一的项目知识信息标准，使用户明确知道“手工应该维护哪一层”。
- 以模块为人工维护的最小单元，支持逐步完善功能点、API、页面原型、包/类、依赖模块等信息。
- 让用户主要维护自然语言名称和业务描述，由系统自动派生内部标识、索引和关联关系。
- 让 Agent 可以稳定读取模块信息，并获取结构化的功能、接口、类包、原型上下文。
- 兼容 Markdown 维护和 Excel 导入两类入口，并收敛到同一事实源。
- 在项目事实信息管理模块中直观展示已维护事实信息，让用户能看见当前知识库内容。

**Non-Goals:**
- 不在本次设计中要求一次性建设完整知识图谱或全量实体关系数据库。
- 不要求用户显式维护所有细粒度实体之间的双向关系，例如类之间依赖、页面到具体类的直接映射。
- 不要求导入工具、Web UI 编辑器、自动迁移脚本在本次变更中全部完成实现。
- 不在本次变更中实现 UI/数据库直接写回模块档案。
- 不在本次变更中实现自动页面摘要生成能力；如需建设，应作为独立工具需求推进。
- 不在本次变更中实现维护完整度评分。

## Decisions

### 1. 采用“模块档案”作为唯一人工维护单元

**Decision**

以模块档案作为唯一权威事实源。一个模块对应一个模块档案，用户围绕同一档案持续补充功能描述、功能点、API 清单、页面原型、包/类、依赖模块等内容。

建议目录形态：

```text
project-facts/
├─ README.md
├─ modules/
│  ├─ 云主机资产管理.md
│  ├─ 告警管理.md
│  └─ ...
└─ generated/
   ├─ module-index.json
   ├─ relation-index.json
   └─ views/
      ├─ modules.md
      ├─ interfaces.md
      └─ ...
```

模块档案使用固定骨架，例如：

```markdown
# 云主机资产管理

## 基本信息
- 所属系统: 网络安全资产管理系统
- 模块状态: 进行中

## 功能描述
...

## 功能点
| 功能点 | 描述 | 状态 |
|---|---|---|

## API 清单
| API 名称 | 说明 | 路径 | 方法 |
|---|---|---|---|

## 页面 / 原型
- 云主机列表页

## 包 / 类
- CloudHostService

## 依赖模块
- 监控中心
```

**Rationale**

这最符合真实维护方式：产品先写模块和功能点，研发随后补 API 和类包，同一模块持续演进。相比“一个大全量 `modules.md` + 多个大全量清单”的方案，模块级变更更局部、冲突更少、用户更容易理解。

**Alternatives considered**

- 保持现有星形总表结构：Agent 读取简单，但人工维护成本高，新增/删除模块需要同步改多个聚合文件。
- 直接以 JSON/数据库为人工维护层：结构化更强，但不利于产品和研发日常手工维护，也不利于代码库内审查和版本比较。

### 2. 区分“人工维护层”和“系统派生层”

**Decision**

用户只维护模块档案。系统从模块档案自动派生：

- 稳定内部标识
- 模块名 / 别名索引
- 模块到功能点、API、页面、包/类的关系索引
- 供 Agent 使用的聚合视图或缓存

派生层不是权威源，不能要求用户手工更新。

**Rationale**

用户应当面向业务名称维护信息，而不是维护 `mod-cloud-host-asset` 这类机器标识。系统自动派生可同时满足低维护成本与高检索精度。

**Alternatives considered**

- 用户显式维护 ID 和引用：结构精确，但维护成本高，极易在日常更新中失真。
- 完全放弃派生层，只让 Agent 读自然语言档案：维护最轻，但检索性能、歧义处理和关系计算会变差。

### 3. 关系以“模块拥有下属信息”为主，跨模块关系轻量显式维护

**Decision**

模块档案内主维护以下内容：

- 功能点
- API 清单
- 页面 / 原型
- 包 / 类
- 依赖模块

系统默认将这些内容解释为：

- 模块 has many 功能点
- 模块 has many API
- 模块 has many 页面 / 原型
- 模块 has many 包 / 类
- 模块 depends on 模块

不要求用户维护大量细粒度交叉关系，例如“某页面具体调用了哪个类”。

**Rationale**

这是一种“弱结构维护、强结构推导”的折中：保留真实工程中最稳定的关系，同时避免把知识库变成高成本图谱录入系统。

**Alternatives considered**

- 每个 API / 类 / 页面都拆成独立事实文件并人工互相引用：表达力强，但录入负担过重。
- 完全不维护关系：成本低，但对 Agent 做影响分析和上下文推荐帮助不足。

### 4. 模块定位基于自然语言名称与别名，而不是用户输入 ID

**Decision**

模块解析入口使用模块名称、别名和派生索引完成。系统自动生成内部主键并维护名称映射；仅在内部逻辑和导出结构中使用，不要求用户输入。

**Rationale**

用户日常讨论的是“云主机资产管理”“告警中心”，不是 `mod-cloud-host-asset`。将 ID 隐藏在系统层，可以显著降低维护门槛并减少命名约束暴露给用户。

**Alternatives considered**

- 继续以模块 ID 作为主要检索入口：对机器友好，但对用户不友好。
- 完全不生成稳定 ID：初期简单，但后续改名、迁移、缓存和跨入口同步都会困难。

### 5. 迁移期保留聚合视图，但其角色退化为生成物

**Decision**

现有 `project-facts/modules.md`、`usecases.md`、`interfaces.md` 等聚合文件在迁移期可以保留，但应改为由模块档案自动生成的视图或缓存，而不是手工维护的权威事实源。

**Rationale**

这既能兼容现有 Agent 读取路径，也为逐步迁移保留缓冲区。实现上可先改“写入方式”，再改“读取方式”，减少一次性切换风险。

**Alternatives considered**

- 一次性删除旧文件：收敛最快，但对当前上下文加载和已有数据兼容风险高。
- 永久双写双维护：最不理想，会继续制造事实源冲突。

### 6. 项目事实信息管理页面以“模块浏览器”方式展示知识库

**Decision**

项目事实信息管理页面应以模块浏览器的方式展示已维护事实信息，而不是仅展示按层级平铺的事实条目列表。默认浏览入口应为模块列表，详情面板应直接展示模块档案中的功能描述、功能点、API 清单、页面/原型、包/类和依赖模块。

建议信息架构：

```text
左侧
├─ 模块搜索
├─ 模块筛选（系统 / 状态 / 完整度）
└─ 模块列表

右侧
├─ 模块基本信息
├─ 功能描述
├─ 功能点
├─ API 清单
├─ 页面 / 原型
├─ 包 / 类
└─ 依赖模块
```

保留按层级或按类型浏览作为辅助视图，而不是主入口。

**Rationale**

用户维护知识库的最小单位是模块档案，因此浏览视角也应与维护视角一致。这样用户可以快速确认“这个模块已经维护了什么、还缺什么”，也更利于后续补充信息。

**Alternatives considered**

- 继续保留“按 layer 的事实项列表”为主：实现简单，但不符合模块档案式知识库的心智模型。
- 完全以图谱或关系网络展示：表达更强，但对当前产品阶段过重，且不利于快速浏览和日常维护。

### 7. 原型文件集中存放，模块内维护“页面名称关联”

**Decision**

原型文件不要求按模块物理拆分存放。对于 Axure 导出的整套 HTML 原型包，系统应允许将其作为一个集中原型资源存放在统一目录中；模块档案只维护与本模块相关的页面名称列表，必要时可附加页面说明，但不要求维护逐页面文件路径。

建议目录形态：

```text
project-facts/
├─ modules/
│  ├─ 云主机资产管理.md
│  └─ ...
└─ prototypes/
   ├─ axure-export/
   │  ├─ index.html
   │  ├─ data/
   │  └─ ...
   └─ page-index.json   # 可选，系统派生的页面名索引
```

模块档案中的原型章节建议为：

```markdown
## 页面 / 原型
- 云主机列表页
- 云主机详情页
- 云主机同步结果页
```

系统可选地从原型包中提取页面名称索引，与模块档案中的页面名称做匹配；若暂时无法自动提取，也允许只把页面名称作为人工维护的关联信息。

**Rationale**

这符合 Axure 的真实交付形态。要求用户把整套原型包再按模块手工拆分，不仅成本高，也容易破坏原型资源结构。让用户只维护“本模块关联哪些页面名称”，维护成本最低，也足以支撑模块级浏览和 Agent 理解。

**Alternatives considered**

- 按模块拆分 Axure HTML 文件：理论上关系更直观，但在实际交付中难以持续维护。
- 只维护原型总包，不维护模块到页面名的关系：存放简单，但无法支持模块视角浏览和上下文关联。

## Risks / Trade-offs

- [模块档案内容过于自由，长期失去统一性] → 通过固定章节骨架、README 模板和导入校验降低自由度。
- [模块名改动导致内部标识和历史引用不稳定] → 系统维护稳定内部 ID，改名时仅更新显示名和别名映射。
- [迁移期新旧格式并存造成混淆] → 明确声明模块档案是唯一权威源，聚合文件仅为生成视图。
- [Excel / UI 导入与 Markdown 手工编辑产生冲突] → 统一收敛到模块档案，并在导入时做覆盖范围提示与差异校验。
- [Agent 读取性能下降] → 使用派生索引和生成视图作为读取缓存，但保留模块档案作为最终事实源。
- [UI 展示与实际事实源脱节] → 事实信息管理页面优先基于模块档案和派生索引渲染，不直接依赖孤立条目列表。
- [原型包无法按模块拆分，导致原型关系难维护] → 采用“原型资源集中存放 + 模块档案维护页面名称”的模型，并支持可选的页面索引派生。

## Migration Plan

1. 定义模块档案标准模板与 README 维护规范。
2. 为现有项目事实信息增加派生索引约定，并标记聚合文件为生成视图。
3. 逐步把现有 `modules.md` / `usecases.md` / `interfaces.md` 等内容迁移为模块档案。
4. 调整模块解析和上下文加载逻辑，使其优先使用模块档案与派生索引。
5. 调整项目事实信息管理页面，使其按模块档案浏览已维护事实信息。
6. 定义原型资源集中存放约定，并支持模块档案维护关联页面名称。
7. 再建设 Excel 导入到模块档案的映射与收敛能力。
8. 在迁移完成后，移除对人工维护聚合文件的依赖。

回滚策略：

- 若新的模块档案读取链路尚不稳定，可临时继续从旧聚合视图读取；
- 模块档案与生成视图并存期间，可重新生成旧视图作为回退输入；
- 在正式移除旧手工格式前，保留完整迁移脚本和数据快照。

## Open Questions

- 模块档案是“一个模块一个 Markdown 文件”还是“一个模块一个目录 + 主文件 + 附件文件”更适合长期演进？
- Excel 导入时，是否以“覆盖整个模块档案”还是“只覆盖特定章节”作为默认行为？
- 页面原型是否默认只维护名称，还是需要标准化到“名称 + 文件路径 + 页面说明”三元结构？
- 是否需要实现 Axure 原型包的自动页面名提取，还是第一期先完全依赖人工维护页面名称列表？
