## Context

当前系统在“文档管理”链路上同时存在三个断点：

1. 正式版本落盘路径与历史查询路径并不总是稳定一致，导致“保存后不可稳定加载”
2. 文档类型在保存、查询、前端筛选三处存在别名分裂，例如 `test` / `test-plan`、`user-guide` / `user-manual`
3. 写作对象名称没有 canonical 规则，同一对象会以“模块名 + 文档后缀”“模块名”“模块/类/包”等多个名字分别落盘

这使得系统虽然已经具备版本化存储能力，但缺少“文档系列”这一稳定主键。用户看到的是同一对象，系统看到的却是多个目录。

## Goals / Non-Goals

**Goals:**
- 明确“保存为正式版本”的唯一官方落盘路径为 `doc_output/`
- 建立一套可复用的 canonical 文档类型体系，统一保存、加载、展示
- 建立一套可复用的 canonical 文档名称体系，解决模块、类、包等对象的多种描述不一致问题
- 保证 `save_document`、`list_documents`、`list_versions`、`load_latest` / `load_saved_document` 使用同一套解析规则
- 保留历史目录读取兼容，避免已有文档立即失效

**Non-Goals:**
- 不做历史文件批量迁移
- 不引入复杂的数据库索引或独立检索服务
- 不实现跨文档的语义聚类或人工合并工作台
- 不在本次变更中支持“按任意历史版本号比较差异”

## Decisions

### 决策 1：以 `doc_output/` 作为唯一官方正式版本根目录

正式保存统一写入：

```text
doc_output/[doc_type]/[canonical_doc_name]/[YYYY-MM-DD]/vX.Y.Z.md
```

这样“保存路径”“列表路径”“加载路径”“前端展示路径”都可由同一规则生成，不再分别依赖不同目录约定。

**备选：** 继续沿用 `backend/docs/`，只修复读写 bug。  
**否决原因：** 历史目录已经混入会话数据与早期实验数据，继续复用会让“正式文档输出”和“系统内部文件”边界更模糊。

### 决策 2：引入 canonical 文档类型集合，并允许别名映射

系统内部只认以下 canonical 类型：

- `requirements`
- `design`
- `test-plan`
- `user-manual`
- `api`
- `general`

对外允许输入别名，例如：

- `req`、`requirement`、`需求规格说明书` → `requirements`
- `test`、`qa`、`测试计划` → `test-plan`
- `user-guide`、`manual`、`操作手册` → `user-manual`

**原因：** 文档类型是目录结构第一层，如果没有 canonical 值，前端筛选、保存目录与历史查询就会天然分叉。

### 决策 3：文档系列使用 canonical 名称，而不是原始标题

保存前先对原始 `doc_name` 做两步处理：

1. **文档后缀剥离**  
   例如“需求规格说明书”“测试方案”“用户手册”“软件设计说明”等只描述文档类型的后缀，从对象名中剥离
2. **对象名称规整**  
   对“模块 / 子模块 / 类 / 包 / 系统 / 服务 / 组件”等泛化后缀做轻量归一，保留对象主体名称

示例：

- `LLM集成管理模块需求规格说明书` → `LLM集成管理模块`
- `用户权限包设计方案` → `用户权限`
- `采购管理类测试计划` → `采购管理`

该 canonical 名称用于目录名和后续系列匹配；原始标题则保留为别名。

### 决策 4：以“别名集 + 轻量模糊匹配”识别同一文档系列

每个文档系列维护一个 `.series.json` 元数据文件，包含：

- canonical `doc_type`
- canonical `doc_name`
- `aliases`
- `updated_at`

保存与查询时均执行：

- 精确匹配：alias 归一后相同
- 包含匹配：一方为另一方核心子串
- 轻量模糊匹配：用于处理空格差异、常见冗余修饰词差异

**原因：** 仅靠精确匹配无法覆盖“LLM 集成管理模块”与“LLM集成管理模块”“模块A需求文档”与“模块A”等真实输入。

**边界：** 本次仅做轻量归一，不尝试基于完整语义理解去合并完全不同的对象。

### 决策 5：历史目录只读兼容，新版本不回写旧目录

系统查询时同时扫描：

- `doc_output/`
- `backend/docs/`
- `docs/`

但只要执行新的正式保存，结果一律落到 `doc_output/`。若历史文档系列只存在于旧目录，则新保存会在 `doc_output/` 下建立同名 canonical 系列继续写入。

**原因：** 这样既保证兼容已有文档，又能让新数据逐步自然收敛到新根目录，而不是继续污染旧目录。

### 决策 6：前端展示以 canonical 信息为主，原始信息作为补充

文档管理页展示：

- canonical 文档类型标签
- canonical 文档名称
- 最新版本与日期
- 实际保存路径
- 别名数量或别名信息

用户不需要理解底层归一过程，但应该能看到“为什么这几个历史名字被视为同一份文档”。

## Risks / Trade-offs

**[风险] 轻量模糊匹配误合并**：两个名字相近但对象不同的文档，可能被误判为同一系列。  
→ 缓解：匹配阈值保守；先用类型隔离，再用 alias / 包含 / 相似度多重约束；优先保留 canonical 名称稳定性。

**[Trade-off] 目录名不再等于用户原始标题**：用户第一次看到路径时，可能发现“文件名被规整了”。  
→ 可接受：这是为了建立稳定系列主键；前端仍显示别名信息帮助用户对照。

**[风险] 历史数据存在不可归一孤岛**：早期错误写入的空名称、异常目录无法自动纠正。  
→ 接受：本次不做批量迁移；后续可单独提供离线修复工具。

## Migration Plan

1. 在 `doc_version_service` 中定义新的 root、canonical 类型映射和 canonical 名称规则
2. 将 `save_document` / `list_documents` / `list_versions` / `load_latest` 统一收敛到同一解析入口
3. 调整 `save-draft` 与 `load_saved_document`，确保 writing_state 和后续保存使用 canonical 名称
4. 更新前端文档管理页的类型筛选、路径展示和别名展示
5. 增加针对 `doc_output`、历史兼容、别名归一的测试

## Consistency Check

本设计要求与 proposal / tasks 对齐如下：

- `proposal` 里声明“官方根目录 = doc_output”，对应本设计“决策 1”
- `proposal` 里声明“canonical 文档类型集合”，对应本设计“决策 2”
- `proposal` 里声明“同一对象不同叫法统一为一个系列”，对应本设计“决策 3 + 决策 4”
- `proposal` 里声明“旧目录只读兼容”，对应本设计“决策 5”
- `tasks` 将按“存储根目录 → 类型归一 → 名称归一 → 前端展示 → 验证”顺序展开，与本设计的决策依赖顺序一致

当前未发现 proposal、design 与预期任务分解之间的直接冲突。
