## Context

当前 document_orchestrator 的 instruction 结构：

```
▸ 文档存在性查询 → 调用 list_saved_documents
▸ 信息查询 → 调用 get_fact_overview / get_fact_detail
▸ 写作/修改文档
  ├── 若有草稿且未保存 → ...
  ├── 若有草稿且已保存 → ...
  └── 若意图不明确 → ask_user
▸ 意图真正模糊 → ask_user
```

这是一棵决策树。模型每轮做的事是：**对当前这句话分类**，然后执行对应分支。

这个结构导致两类失败：

**失败 1：指代词解析**
```
Round 1: "介绍一下技能管理模块" → 正确回答
Round 2: "查询一下这个模块最新版本的用户手册"
  → 模型读到"这个模块"，没有匹配到任何已知实体
  → 触发"意图模糊"分支 → ask_user("哪个模块？")
  → 实际上 Round 1 已经建立了"技能管理模块"这个实体
```

**失败 2：澄清循环中意图丢失**
```
Round 2: 原始意图 = 查用户手册（list_saved_documents）
  → Agent 触发澄清子循环
Round 3: 用户答"技能管理模块"
  → 模型对 Round 3 独立分类 → 匹配"信息查询"分支
  → 调用 get_fact_detail，输出模块介绍
  → 原始意图"查用户手册"彻底丢失
```

## Goals / Non-Goals

**Goals:**
- 主 Agent 能从对话历史解析指代词，不重复询问已建立的实体
- 澄清循环闭合：收到澄清回答后，合并回原始意图继续执行
- 降低 instruction 决策树密度，让模型自然推理替代规则分支

**Non-Goals:**
- 不引入外部实体追踪数据结构（靠 instruction + 模型能力解决）
- 不修改工具列表
- 不修改 Sub-agent 的任何逻辑

## Decisions

### 决策 1：instruction 基调从"分类器"改为"对话伙伴"

**旧基调：**
```
你的职责是：理解用户请求 → 判断意图类型 → 执行对应分支
```

**新基调：**
```
你是一个持续对话的文档助手。
每一轮用户输入都是整段对话的延续，不是独立的新请求。
```

这一句话的改变，让模型的处理方式从"分类当前句"变为"理解当前句在对话中的含义"。

### 决策 2：显式写入指代词解析规则

作为 instruction 中的硬性约束：

```
【对话连续性规则】
- 用户使用"这个/这/它/该/上面说的/刚才提到的"等指代词时，
  必须从会话历史中解析其指代的具体对象，不得向用户重新询问
  已在本次对话中明确过的信息
- 本轮对话中已经确认的实体（模块名、文档类型、版本等），
  后续轮次直接沿用，无需用户重复说明
```

### 决策 3：澄清循环闭合规则

```
【澄清循环规则】
- 当你向用户提出澄清问题后，用户的下一条回答是对你问题的答案，
  不是新的独立请求
- 收到澄清回答后：将答案填入你提问前的原始意图，继续执行原始任务
- 不得对澄清回答重新做意图分类
```

这两条规则优先级高于所有意图分类逻辑。

### 决策 4：降低决策树密度

将当前的 if-else 分支结构改为"意图识别 + 工具映射"结构：

**旧结构（分支式）：**
```
▸ 文档存在性查询 → list_saved_documents
▸ 信息查询 → get_fact_overview
▸ 写作场景
  ├── 有草稿未保存 → user_intent 注明...
  └── 有草稿已保存 → user_intent 注明...
```

**新结构（原则式）：**
```
理解用户的最终目标，选择最合适的工具或 Skill：
- 查文档是否存在 → list_saved_documents
- 查项目信息 → get_fact_overview / get_fact_detail
- 写作 → execute_skill（草稿状态通过 draft_hint 传入，Sub-agent 自行决策）
- 信息不足才问 → ask_user
```

分支细节（"有草稿未保存时怎样"）下沉到 Sub-agent，Orchestrator 只做高层决策。

## Risks / Trade-offs

- **规则减少后可能出现新的漏洞**：靠原则替代规则，模型需要推理，某些边缘情况可能处理不一致 → 通过测试观察，按需补充最小约束
- **澄清循环规则可能被误触发**：如果用户真的在换话题，模型可能仍把它当澄清回答处理 → instruction 中补充"若用户明显转换话题（如出现新的动词+对象组合），视为新请求"
