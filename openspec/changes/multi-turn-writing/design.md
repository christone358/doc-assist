## Context

当前 Agent 每轮对话独立处理，不维护写作过程中的状态。`stream_message()` 每次都重新识别模块、重新加载项目事实、把最近5轮对话历史传入 LLM。这导致：

- 后续修改轮次中模块识别经常出错（当前消息无模块关键词时 LLM 误判）
- Token 随轮数线性增长（每轮历史 + 每轮事实重新加载）
- 文档生成后立即落盘，用户无法在确认前继续调整

目标是引入**文档驱动的多轮对话机制**：对话持有当前写作状态，后续修改以最新草稿为上下文，而非对话历史。

## Goals / Non-Goals

**Goals:**
- 写作状态（当前模块、草稿内容）跨轮次持久
- 修改轮次 token 消耗恒定，不随轮数增长
- 草稿与正式版本分离，用户显式保存才落盘
- 快捷操作按钮（保存）非阻塞，不影响继续对话
- 定位模块时自动加载最新已保存版本作为写作基准

**Non-Goals:**
- 不支持同一对话内并行编写多个不同文档（多文档 = 新对话）
- 不实现版本 diff 展示（已有独立需求）
- 不支持协作编辑

## Decisions

### 决策1：以「当前草稿」替代「对话历史」作为修改轮次的主上下文

**选择**：修改轮次时，LLM 输入为 `当前草稿全文 + 用户修改请求`，不传入历史轮次记录。

**理由**：文档写作中，最新版本的文档本身已经编码了所有已生成的知识，历史对话仅是编辑指令的记录，对 LLM 生成下一版没有实质增量价值。传入历史只会线性增加 token。

**对比方案**：继续传历史记录（最近 N 轮）→ token 持续膨胀，且历史中的旧版文档片段会造成混淆。

---

### 决策2：WritingState 挂载在 ConversationInfo 上

**选择**：`ConversationInfo` 新增 `writing_state: Optional[WritingState]` 字段，随对话持久化。

**理由**：写作状态与对话生命周期一致，复用现有持久化机制（JSON 文件），无需额外存储。

**对比方案**：单独的写作状态存储 → 增加存储层复杂度，且生命周期与对话解耦会导致孤儿状态。

---

### 决策3：草稿驻留内存，显式保存才落盘

**选择**：LLM 生成结果更新 `writing_state.draft_content`，不触发文件写入。后端提供 `save-draft` API，用户点击「保存」按钮才调用。每次保存递增版本号（v1.0 → v1.1）。

**理由**：用户在满意之前可能经过多轮调整，每轮都落盘会产生大量中间版本噪音。显式保存给用户明确的控制感。

**对比方案**：自动保存每轮 → 版本目录膨胀，用户无法区分"过程版本"和"满意版本"。

---

### 决策4：LLM 判断写作意图，驱动流程分支

**选择**：每轮在意图识别阶段，LLM 判断为以下三种之一：
- `modify`：修改/增量，沿用当前 writing_state，走轻量流程
- `new_module`：明确要写新模块，清空 writing_state，走全量流程
- `rewrite`：全部重写，保留 module_id，重新加载项目事实

**理由**：意图判断已经有 `_identify_intent()` 的基础，在此扩展比用规则匹配更能应对自然语言的多样性。

---

### 决策5：历史版本自动作为写作基准

**选择**：全量流程定位模块后，检查 `docs/[doc_type]/[module_name]/` 目录，若存在已保存版本则加载最新版内容作为 `draft_content`，状态提示用户。

**理由**：用户重新开启对同一模块的写作时，已有历史版本是最自然的起点，无需重新生成。

## Risks / Trade-offs

- **草稿丢失**：用户关闭浏览器后草稿内存丢失。→ 接受，已与用户对齐：未保存即视为放弃，已保存版本可随时恢复。
- **大文档 token 上限**：文档超长时（如 8000+ tokens）会触发模型上下文限制。→ MVP 阶段不处理，可后续加入文档摘要/章节切分机制。
- **意图判断误差**：LLM 意图判断偶尔出错，将修改请求误判为新模块。→ 在 status step 中展示当前 writing_state（模块+版本），用户可验证，并可用"重新开始"指令显式重置。

## Open Questions

- `rewrite` 意图是否需要二次确认？（"您确定要全部重写吗？已有草稿将丢失"）→ MVP 先不做，直接重写。
