## Context

当前对话页右侧过程明细主要由 [ObservabilityPanel.svelte](/Users/chris/Documents/dev/nextAgent/doc-assit/frontend/src/lib/components/ObservabilityPanel.svelte) 中的 `buildItems()` 将事件流按时间顺序归并成若干 step/card。这个实现能展示“发生过什么”，但不能稳定回答三个更关键的问题：

- 当前展示对象是谁，是主 Agent、子 Agent、某次工具调用，还是某段思考
- 一个对象的完整执行过程是什么，尤其是工具输入、工具输出和 Skill 下的子过程
- 哪些思考内容可以作为详细记录展示，哪些属于不应该直接暴露的内部 reasoning

现状还有三个结构性缺口：

- 工具调用缺少实例标识，前端只能靠 `tool name + 最近 step` 猜测归属
- 工具详情事件大多只有摘要，没有标准化输入/输出/详情字段
- Skill 只有 `skill_start` / `subagent_start` 标记，没有作为父级容器承载下属执行对象

同时，现有执行链路相关设计已经明确要求展示层不得直接暴露原始内部 reasoning，因此这次设计必须同时满足“更详细”和“仍然安全可展示”两个约束。

## Goals / Non-Goals

**Goals:**

- 将右侧过程明细重构为按执行对象分组的视图，而不是混合时间线
- 为 `LLM 思考`、`工具调用`、`Skill 调用`、`用户提问`、`系统状态` 建立稳定的数据契约和渲染模型
- 让工具调用能够清晰呈现输入、输出摘要和可折叠详情
- 让 Skill 调用成为父级执行容器，能够承载子 Agent 的思考和工具链路
- 明确“可展示的详细思考记录”与“不可展示的 raw reasoning”边界
- 保持左侧结果区和右侧过程区的边界不变，避免正式正文再次混入过程视图

**Non-Goals:**

- 不在本次设计中暴露 provider 原始 chain-of-thought、隐藏 reasoning token 或其他不可控内部推理文本
- 不重做左侧消息气泡、文档产物区和保存流程
- 不实现过程明细的跨轮聚合、检索、导出或长期持久化查询能力
- 不把最终文档正文完整复制到右侧工具输出详情中

## Decisions

### Decision 1: 引入“执行对象节点”模型，替代基于时间线的启发式拼接

后端和前端之间新增统一的“执行对象节点”契约。每个可展示对象至少包含：

- `node_id`: 当前对象实例的稳定标识
- `parent_node_id`: 父对象标识；Skill 下的工具/思考节点指向所属 Skill
- `type`: `llm_thought`、`tool_call`、`skill_call`、`user_question`、`system_state`
- `actor`: `orchestrator`、`subagent`、`runtime`
- `title`: 展示标题
- `status`: `started`、`completed`、`failed`
- `source`: 工具来源或对象来源，如 `mcp`、`builtin`
- `detail`: 与对象类型相关的结构化字段

右侧面板不再从“事件文本”推导对象，而是先构造节点树，再按节点类型渲染。

其中：

- `user_question` 用于承载需要用户明确回复的澄清问题
- `system_state` 用于承载完成、失败、等待用户回复等关键系统状态

选择节点树而不是继续增强 `buildItems()` 的时间线启发式，是因为当前问题已经不是样式问题，而是数据模型失真。只靠“最近一个 step”“相同 tool name”之类的规则，无法稳定承载嵌套 Skill 和多个重复工具调用。

备选方案：

- 继续沿用当前时间线结构，仅在前端增加更多归并规则：实现快，但会继续累积特殊判断，复杂度失控
- 完全改成瀑布式 span 日志：能保留顺序，但对象边界仍然模糊

### Decision 2: 将“详细思考内容”定义为可展示思考记录，而不是 raw CoT

本次设计接受“思考要展示详细输出内容”的产品诉求，但只限于运行时明确发出的、可展示的思考记录。也就是说：

- 右侧可以展示完整的 `thinking` 文本块
- 这些文本块可以作为单独的 `llm_thought` 节点展开查看
- 但不得直接透传 provider 原始 chain-of-thought、隐藏 reasoning 或模型内部未经过滤的中间思维

这样既能满足“要看到较详细的思考内容”，又不违反现有安全边界和执行链路规格。

备选方案：

- 直接展示 raw CoT：和现有规格冲突，且会引入安全、稳定性和供应商兼容性问题
- 只保留一行摘要：无法满足本次希望查看详细过程的诉求

### Decision 3: 工具调用节点固定展示“输入 + 输出摘要 + 可折叠详情”

每个 `tool_call` 节点统一采用以下结构：

- 标题：`工具名称 + 执行状态`
- 元信息：工具来源、执行 actor、耗时
- 输入：结构化参数或可读摘要
- 输出摘要：面板默认可见的简短结果
- 详情：可折叠的详细输出

其中“详情”允许是完整文本，也可以是经过截断或筛选后的详细信息。对于体积过大或不适合右侧复制展示的结果，例如 `write_document` 生成的正式正文，只展示摘要、字数、目标模块、草稿更新状态等元信息，不把完整正文塞进过程面板。

进入右侧面板前，工具观测数据必须经过“可展示化”处理：

- 工具节点只接收 `display_input`、`output_preview`、`output_detail` 这类 UI 字段，不直接透传原始参数对象或原始返回体
- 若输入中包含大段用户原文、handoff 提示词、文件正文、草稿正文或其他高体积内容，必须改为摘要或元信息
- 若输出体积过大，`output_detail` 必须截断，并优先保留摘要、统计值、命中对象、路径、状态等高价值字段
- 对包含敏感字段、绝对路径、内部 prompt 片段或不适合展示的上下文，必须在后端先脱敏或替换为说明文本

备选方案：

- 只展示工具结果摘要：用户仍然看不到“工具到底收到什么输入”
- 直接展示完整输入和完整输出：大多数工具可以，但 `write_document` 之类会造成结果区与过程区重复

### Decision 4: Skill 调用节点作为父级容器，聚合其下属执行对象

`skill_call` 节点不再只是“开始执行某个 Skill”的单条状态，而是一个可展开的父级对象，至少包含：

- Skill 名称
- 执行状态
- 选择原因
- 交接摘要
- 子节点列表：该 Skill 下的思考节点和工具节点

渲染顺序上，用户先看到 Skill 容器，再在容器内部展开其调用链。这样能回答“这次 Skill 到底做了什么”，也能避免子 Agent 产生的 thinking/tool 继续漂浮在时间线上。

归属规则上，某个对象一旦归属于某个 Skill 容器，就只在该 Skill 容器内部展示，不在顶层重复渲染。

对 `user_question` 和 `system_state` 采用更细的归属规则：

- 若问题或状态只描述某个 Skill 内部执行阶段，例如“需要确认该 Skill 的目标模块”“该 Skill 执行失败”，则归属于对应 Skill 容器
- 若问题或状态描述整轮会话级流程，例如“等待用户继续输入”“本轮处理完成”“主 Agent 执行失败”，则作为顶层对象展示
- 同一个语义状态只允许出现一个主展示对象；如果已经通过 Skill 节点状态表达，就不再额外生成同语义顶层 `system_state`

备选方案：

- 仅保留 `skill_start` badge：无法承担执行容器职责
- 单独展示 `subagent_start`，其余子过程仍平铺：对象边界仍不清晰

### Decision 5: 以前端归一化层兼容旧事件，并逐步切换到新节点契约

考虑当前后端已有 `status(tool_call/detail)`、`execution_event`、`thinking`、`skill_start`、`subagent_start` 等多种事件，本次不要求一次性删除旧类型，而是：

- 后端优先为这些事件补充节点字段
- 前端新增归一化层，优先消费新节点数据
- 在缺少节点字段的情况下，短期保留旧时间线回退逻辑

这样可以降低迁移风险，并允许按工具模块逐步补齐输入/输出数据。

备选方案：

- 一次性切换到全新事件类型并删除旧字段：实现更纯粹，但上线风险高

### Decision 6: “完整思考文本”仅指完整的可展示思考记录

规格中出现的“完整思考文本块”“详细思考内容”，统一指运行时显式发出的、允许展示的思考记录全文，而不是“尽可能接近模型内部全部推理过程”的意思。

这样可以避免把“更详细”误解成“更接近 raw reasoning”，也与既有的安全边界保持一致。

### Decision 7: 对象顺序按创建时间稳定排序，不按类型重排

右侧面板的顶层对象按对象首次创建时间升序展示；Skill 容器内部的子对象也按首次创建时间升序展示。前端不得为了视觉分组再按对象类型二次重排。

这样可以保留执行链路的自然顺序，同时避免“对象化以后顺序随类型漂移”的问题。状态更新只更新已有对象内容和状态，不改变其原始位置。

备选方案：

- 按对象类型分组排序：视觉上整齐，但会破坏真实执行顺序
- 按最后更新时间排序：状态一更新就跳动位置，阅读体验差

### Decision 8: 工具节点采用“固定最小字段 + 允许扩展字段”契约

为了避免不同工具因为“适合时/可行时”而输出形态不一致，每个 `tool_call` 节点最少必须包含以下 UI 字段：

- `display_input`: 可展示输入摘要，不能为空
- `output_preview`: 可展示输出摘要，不能为空
- `output_detail`: 可折叠详情；可为空，但字段必须存在

允许扩展字段包括：耗时、命中对象、资源路径、统计值、来源 server、退出码等。

例外规则只有两类：

- 正式正文类工具：`output_detail` 不承载正文全文，只承载摘要与元信息
- 零输出类工具：若工具本身没有可展示结果，也必须返回显式的结果说明，而不是省略 `output_preview`

### Decision 9: 历史轮次通过回退归一化保持可读，而不是要求旧数据迁移

考虑仓库里已经存在大量只有旧事件格式的历史轮次，本次不要求一次性迁移所有历史数据，而是采用“双通道回放”：

- 新轮次优先消费对象节点字段
- 历史轮次若缺少节点字段，则前端使用旧事件回退归一化逻辑构造只读对象视图
- 回退构造的对象不要求补齐全部增强字段，但必须保证问题、状态、Skill 和工具链路可读

这样可以避免为了 UI 重构引入历史数据迁移工程，也能保证新老对话都能打开。

### Decision 10: 过程明细字段采用预算控制，不透传无上限 detail

对象化后，最容易失控的是 `output_detail`、大型 `display_input` 和持久化后的历史体积。因此本次要求后端对可展示字段实施预算控制：

- WebSocket 流式消息只发送预算内的可展示字段，不发送原始全文对象
- 持久化到会话历史的数据沿用同一套预算后的字段，而不是额外保存原始 detail
- 超出预算的 detail 必须截断，并附带“已截断”语义提示

这里的“预算”可以是字符数、字节数或对象深度限制，具体阈值可在实现阶段确定，但约束本身必须成立。

### Decision 11: 系统状态节点使用显式映射表，避免父节点状态和独立状态节点重复表达

`system_state` 不应该成为任何状态都能往里塞的兜底桶。本次采用映射表思路：

- Skill 内部失败：优先更新 `skill_call.status`，必要时仅在 Skill 容器内补一个子级 `system_state`
- 主链路失败：生成顶层 `system_state`
- 等待用户回复：生成 `user_question`；若仅是问题发出后的等待，不再额外生成同语义 `system_state`
- 整轮完成：优先以顶层 `system_state` 表达一次，不为每个父节点重复生成“完成”节点

这样可以避免“一个失败同时出现父节点 failed + 顶层 failed + 子级 failed”的重复状态污染。

## Risks / Trade-offs

- [Risk] 工具输入输出明细会显著增加事件体积 → Mitigation：区分 `preview` 和 `detail`，对大文本做截断与分类展示
- [Risk] `write_document` 一类工具的完整输出会与左侧正文重复 → Mitigation：对正式正文类工具只展示摘要和元信息，不在右侧复制正文
- [Risk] 旧事件模型和新节点模型并存，会让前端归一化逻辑暂时变复杂 → Mitigation：新增单独的 normalization 层，并在验证完成后逐步删除旧分支
- [Risk] “详细思考内容”容易被误解为 raw CoT → Mitigation：在规格和实现中统一使用“可展示思考记录”术语，并禁止直接透传 provider 原始 reasoning
- [Risk] 多次连续调用同一工具时，节点归属仍可能混淆 → Mitigation：后端为每次工具调用生成稳定 `node_id`，前端不再依赖 tool name 猜测归属
- [Risk] 顶层与 Skill 容器内同时展示同一对象，会造成重复渲染和用户困惑 → Mitigation：明确“属于 Skill 的对象仅在 Skill 容器内展示”的单一归属规则
- [Risk] 对象化后若缺少排序规则，不同实现会产生不同阅读顺序 → Mitigation：固定按对象首次创建时间排序，禁止按类型重排
- [Risk] 工具节点字段不统一会导致不同工具展示碎片化 → Mitigation：定义 `display_input`、`output_preview`、`output_detail` 的最小必填契约
- [Risk] 历史轮次若只支持新节点模型，会出现旧对话无法回放 → Mitigation：保留旧事件回退归一化逻辑，保障历史轮次只读可见
- [Risk] 明细字段无预算控制会放大 WebSocket、存储和前端渲染成本 → Mitigation：对 `display_input` / `output_preview` / `output_detail` 实施统一预算与截断策略
- [Risk] `system_state` 若无明确映射表，会与父节点状态重复表达 → Mitigation：按会话级/Skill级语义建立状态生成白名单

## Migration Plan

1. 为执行链路新增对象节点模型，并在后端事件中补充 `node_id`、`parent_node_id`、`type`、`status`、`detail`
2. 先改造主 Agent 和子 Agent 的工具发射逻辑，确保工具开始/完成事件都能绑定到同一对象实例
3. 为思考、Skill、工具三类对象补齐展示所需字段，明确哪些字段可以进入右侧详情
4. 在前端新增归一化层和新的右侧对象树渲染逻辑，同时保留旧事件回退路径
5. 明确工具输入输出的脱敏、摘要和截断规则，并对高体积工具逐个补齐 UI 字段
6. 为历史轮次保留回退归一化路径，确保旧对话在新面板中仍可只读回放
7. 补充验证：普通查询、事实检索、Skill 写作、澄清中断、重复工具调用、失败场景
8. 在新面板稳定后，删除旧 `buildItems()` 中依赖时间线启发式的主路径

回滚策略：

- 若节点模型或新面板存在严重兼容问题，可切回旧的时间线归并逻辑
- 后端可以继续发送旧事件格式；新字段视为增量增强，不要求立即中断旧链路

## Open Questions

- `write_document` 的输出详情是否需要提供“查看草稿摘要”入口，还是只显示写入结果元信息；本次先按“仅摘要，不复制正文”处理
- 工具详情默认展开哪些部分：输入展开、输出摘要展开、完整详情折叠，还是全部折叠；本次默认完整详情折叠
- 是否需要在右侧面板中显式展示对象耗时和 token 消耗到每个节点级别；本次设计预留字段，但不要求首版全部实现
