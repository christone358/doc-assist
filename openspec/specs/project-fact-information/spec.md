## ADDED Requirements

### Requirement: 项目事实信息三层组织结构
项目事实信息 SHALL 以星形模型组织，modules.md 作为枢纽和检索入口，其他清单文件通过模块 ID 标签与模块关联。分层披露原则体现在条目内部的信息密度分层，而非目录层级分离。

#### Scenario: 星形存储结构
- **WHEN** 用户维护项目事实信息时
- **THEN** `project-facts/` 目录 SHALL 包含以下文件：
  - `modules.md` — 模块树，每个条目包含模块 ID、名称、描述、关联资源引用
  - `usecases.md` — 所有用例，每条含 `模块: {id}` 标签
  - `classes.md` — 所有类包，每条含 `模块: {id}` 标签
  - `interfaces.md` — 所有接口，每条含 `模块: {id}` 标签
  - `prototypes/` — 原型文件，命名规则为 `{module-id}.*`
  - `README.md` — 系统词汇表和格式规范

#### Scenario: modules.md 作为双重职责文件
- **WHEN** Agent 读取 modules.md 时
- **THEN** 该文件 SHALL 同时满足：
  1. 对 LLM：提供项目全貌（模块树结构、模块描述）
  2. 对 Agent：提供检索入口（模块 ID、关联资源路径引用）
  每个模块条目格式示例：
  ```markdown
  ### 登录模块 {#auth-login}
  别名: 用户登录, 用户认证
  负责用户认证和会话管理。
  关联资源:
  - 用例: UC-001, UC-002
  - 核心类: AuthService, PasswordValidator
  - 接口: POST /api/auth/login
  - 原型: prototypes/auth-login.html
  - 源码目录: src/auth/login/
  ```

#### Scenario: 清单文件条目包含摘要和详情两个层次
- **WHEN** Agent 读取清单文件中的条目时
- **THEN** 每个条目 SHALL 包含摘要行（供快速了解）和详细描述（供深度理解），Agent 可选择读取深度

#### Scenario: 关系通过模块条目单点维护
- **WHEN** 用户需要建立知识要素之间的关联时
- **THEN** 所有跨要素关联 SHALL 只在 modules.md 的模块条目中声明，usecases.md / classes.md 等文件的条目只需包含自身内容和模块归属标签，不需要交叉引用

### Requirement: 项目事实信息的查询接口
系统应该提供清晰的查询接口，让Agent能够高效地查询所需信息。

#### Scenario: 按层级查询
- **WHEN** Agent 需要查询项目事实信息时
- **THEN** 应该提供以下查询方式：
  1. **按层级查询**：`GET /project-facts/layer/{level}` - 获取指定层级的所有信息
  2. **按类型查询**：`GET /project-facts/type/{type}` - 获取特定类型的信息（如所有用例、所有模块）
  3. **按ID查询**：`GET /project-facts/item/{id}` - 获取特定ID的详细信息

#### Scenario: 关键词搜索
- **WHEN** Agent 需要找到相关的事实信息时
- **THEN** 系统应该支持：
  1. **全文搜索**：按关键词搜索所有事实信息
  2. **分面搜索**：按层级、类型、关键词组合搜索
  3. **返回关联信息**：搜索结果应包含各层级的关联信息

#### Scenario: 信息关联查询
- **WHEN** Agent 需要了解事实信息之间的关系时
- **THEN** 系统应该支持：
  1. **获取相关项**：给定一个用例，找到相关的模块、接口、用户故事
  2. **获取层级路径**：给定一个具体项，找到其在层级中的完整路径
  3. **获取依赖**：获取某模块或接口的所有依赖关系

### Requirement: 项目事实信息的版本管理
项目事实信息可能会随时更新，系统应该支持版本管理，让Agent知道信息的有效期。

#### Scenario: 版本追踪
- **WHEN** 项目事实信息被更新时
- **THEN** 系统应该：
  1. 记录每次更新的时间和版本号
  2. 保留历史版本（可选）
  3. 标记最新的有效版本

#### Scenario: 版本通知
- **WHEN** Agent 使用事实信息时
- **THEN** Agent 应该：
  1. 知道当前使用的信息版本
  2. 如果信息已更新，收到提示
  3. 能够选择使用新版本或继续使用旧版本

### Requirement: 项目事实信息的只读保护
项目事实信息由人工维护，Agent 不能修改或删除。

#### Scenario: 访问控制
- **WHEN** Agent 操作项目事实信息时
- **THEN** 系统应该：
  1. 仅允许读取操作
  2. 拒绝所有写入、修改或删除操作
  3. 记录所有查询操作（用于审计）

#### Scenario: 错误信息反馈
- **WHEN** Agent 发现事实信息可能有误时
- **THEN** Agent 应该：
  1. 不能自行修改或标记为无效
  2. 向用户报告发现的问题
  3. 建议用户联系项目管理人员进行修正

### Requirement: 项目事实信息的展示和导航
Web UI 应该清晰地展示项目事实信息，帮助用户理解和浏览。

#### Scenario: 事实信息浏览
- **WHEN** 用户访问项目事实信息浏览页面时
- **THEN** Web UI 应该：
  1. 以树形结构展示清单层
  2. 支持展开/折叠各层级
  3. 点击任何项可查看其详细信息
  4. 显示该项在各层级中的位置

#### Scenario: 快速导航
- **WHEN** 用户在查看文档编写时
- **THEN** Web UI 应该：
  1. 显示相关的项目事实信息链接
  2. 允许快速跳转到事实信息的详细页面
  3. 支持在对话中插入引用（如"这个功能的接口定义是..."）

### Requirement: Agent 对事实信息的智能使用
Agent 应该在适当的时候自动推荐和使用项目事实信息。

#### Scenario: 需求分析时的信息推荐
- **WHEN** Agent 分析用户的文档编写需求时
- **THEN** Agent 应该：
  1. 识别用户需求涉及的模块、用例、接口
  2. 自动查询相关的事实信息
  3. 向用户展示"推荐的相关信息"

#### Scenario: 文档内容的事实引用
- **WHEN** Skill 生成文档内容时
- **THEN** Skill 应该：
  1. 从事实信息中提取准确的内容
  2. 在文档中标注引用来源（如"模块X的接口定义为..."）
  3. 确保文档内容与事实信息保持一致

#### Scenario: 修改影响分析
- **WHEN** 用户请求修改文档时
- **THEN** Agent 应该：
  1. 查询事实信息，分析修改可能的影响范围
  2. 提示用户可能需要同时修改的相关部分
  3. 建议修改的顺序和优先级

### Requirement: 项目事实信息格式规范
`project-facts/README.md` SHALL 提供完整的格式规范，指导用户正确维护项目事实信息。

#### Scenario: 词汇表文档化
- **WHEN** 用户查阅 README.md 时
- **THEN** README.md SHALL 包含系统词汇表，说明每个词汇对应的文件和检索方式

#### Scenario: 各清单文件的条目格式示例
- **WHEN** 用户新增条目时
- **THEN** README.md SHALL 为每种清单文件提供标准条目格式示例，包括必填字段（模块标签、名称、摘要）和可选字段
