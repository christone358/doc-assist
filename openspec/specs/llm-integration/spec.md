## ADDED Requirements

### Requirement: 支持多个 LLM 模型提供商
LLM 集成模块应该支持多个 LLM 模型提供商，当前支持 DeepSeek 和 QWen。

#### Scenario: DeepSeek 模型支持
- **WHEN** 用户选择使用 DeepSeek 模型时
- **THEN** 系统应该支持：
  1. DeepSeek 提供的各种模型版本（如 DeepSeek-V3、DeepSeek-R1 等）
  2. 通过 DeepSeek API 进行调用
  3. 支持 DeepSeek 的深度思考模式（如支持）

#### Scenario: QWen 模型支持
- **WHEN** 用户选择使用 QWen 模型时
- **THEN** 系统应该支持：
  1. QWen 提供的各种模型版本（如 QWen-plus、QWen-max 等）
  2. 通过 QWen API 进行调用
  3. QWen 模型的推理和处理能力

#### Scenario: 模型切换
- **WHEN** 用户需要切换使用的 LLM 模型时
- **THEN** 系统应该：
  1. 支持在多个已配置的模型间切换
  2. 切换时不影响对话历史和状态
  3. 支持设置默认使用的模型

### Requirement: LLM 模型配置管理
系统应该提供灵活的 LLM 模型配置管理，让用户可以配置和管理多个 LLM 模型。

#### Scenario: 配置基本信息
- **WHEN** 用户添加或配置一个 LLM 模型时
- **THEN** 系统应该支持配置以下信息：
  1. **模型提供商** - 选择 DeepSeek 或 QWen
  2. **模型名称** - 具体的模型版本（如 deepseek-chat、qwen-max）
  3. **API 地址** - LLM 服务的 API 端点
  4. **API 令牌** - 调用 API 所需的认证令牌/密钥
  5. **配置名称** - 此配置的标识名（如"生产环境 DeepSeek"）

#### Scenario: 配置模型参数
- **WHEN** 用户配置 LLM 模型的运行参数时
- **THEN** 系统应该支持配置：
  1. **温度（Temperature）** - 控制生成内容的多样性（0-2）
  2. **最大令牌数（Max Tokens）** - 单次响应的最大长度
  3. **Top-P** - 核采样参数（0-1）
  4. **频率惩罚（Frequency Penalty）** - 控制重复词汇
  5. **存在惩罚（Presence Penalty）** - 控制新词的引入
  6. **其他模型特定参数** - 不同模型提供商的专有参数

#### Scenario: 配置存储和加载
- **WHEN** 用户保存 LLM 配置后
- **THEN** 系统应该：
  1. 将配置持久化保存（到配置文件或数据库）
  2. 应用启动时自动加载已保存的配置
  3. 支持多配置并存（可同时配置多个模型）
  4. 支持导入/导出配置

#### Scenario: 配置验证
- **WHEN** 用户提交 LLM 配置时
- **THEN** 系统应该：
  1. 验证必需字段是否完整（API地址、令牌等）
  2. 验证 API 地址的格式
  3. 可选：测试 API 连接和认证是否成功
  4. 如验证失败，提供清晰的错误信息

#### Scenario: 敏感信息保护
- **WHEN** 存储和管理 API 令牌时
- **THEN** 系统应该：
  1. 对 API 令牌进行加密存储
  2. 在 UI 上显示令牌时进行掩码（如显示末尾几个字符）
  3. 不在日志或错误信息中暴露完整的令牌
  4. 支持定期更新令牌

### Requirement: LLM 调用的错误处理和降级
系统应该妥善处理 LLM 调用失败的情况。

#### Scenario: API 调用失败
- **WHEN** LLM API 请求失败（超时、网络错误、认证失败等）
- **THEN** 系统应该：
  1. 记录详细的错误日志
  2. 返回用户友好的错误提示
  3. 区分不同的错误类型并提供相应的解决建议
  4. 支持自动重试（指数退避）

#### Scenario: 令牌限制处理
- **WHEN** LLM API 返回令牌限制相关错误时
- **THEN** 系统应该：
  1. 检测是否达到速率限制
  2. 实现请求队列和限流
  3. 向用户提示预计等待时间
  4. 支持管理员配置请求限流策略

#### Scenario: 模型不可用降级
- **WHEN** 配置的 LLM 模型无法使用时
- **THEN** 系统应该：
  1. 检测是否有其他已配置的可用模型
  2. 如有备选模型，自动切换到备选模型
  3. 通知用户模型已自动切换
  4. 记录模型不可用事件

### Requirement: LLM 集成模块接受用户输入
LLM 集成模块应该接收来自 Web UI 的用户自然语言输入，并将其传递给 LLM 进行处理。调用完成后 SHALL 返回 token 用量数据。

#### Scenario: 接收输入
- **WHEN** Agent 收到用户的自然语言输入
- **THEN** LLM 集成模块应该接收该输入，并准备调用 LLM API

#### Scenario: 输入验证
- **WHEN** LLM 集成模块接收用户输入时
- **THEN** 应该验证输入的长度和格式，防止异常的请求

#### Scenario: 非流式调用返回 token 用量
- **WHEN** 通过 complete() 方法完成一次 LLM 非流式调用
- **THEN** 返回值 SHALL 包含响应文本和 token 用量信息（prompt_tokens、completion_tokens、total_tokens）

#### Scenario: 流式调用结束后提供 token 用量
- **WHEN** 通过 stream_complete() 方法完成流式 LLM 调用
- **THEN** 流式输出结束后 SHALL 提供本次调用的 token 用量；若 provider 不支持流式 usage，则用量数据为 None

### Requirement: LLM 理解和提取需求信息
LLM 应该能够理解用户的自然语言描述，提取结构化的需求信息（文档类型、项目背景、特定要求）。

#### Scenario: 需求解析
- **WHEN** LLM 接收到用户的文档需求描述
- **THEN** LLM 应该识别出文档类型、关键需求、上下文信息等

#### Scenario: 多语言支持
- **WHEN** 用户用中文输入需求
- **THEN** LLM 应该正确理解中文意图并提取信息

### Requirement: LLM 协助 Agent 决策调度合适的 Skill
LLM 应该根据解析的需求信息，协助 Agent 决策选择哪个 Skill 最适合完成任务。

#### Scenario: Skill 推荐
- **WHEN** LLM 完成需求分析后
- **THEN** LLM 应该推荐最适合的 Skill（如：用户需要"架构设计文档"，推荐"技术设计文档 Skill"）

#### Scenario: 置信度评估
- **WHEN** LLM 进行推荐时
- **THEN** LLM 应该提供推荐的置信度评分，如果置信度低应该提供多个备选项

### Requirement: LLM 协助提取 Skill 参数
LLM 应该从用户输入中提取 Skill 所需的参数值，减少用户需要手动输入的工作。

#### Scenario: 参数提取
- **WHEN** 推荐的 Skill 需要特定参数（如项目名称、背景信息）
- **THEN** LLM 应该尝试从用户输入中提取这些参数值

#### Scenario: 参数补全
- **WHEN** 某些必需参数无法从用户输入中提取
- **THEN** LLM 应该生成清晰的问题提示，要求用户补充缺失的信息

### Requirement: LLM 错误恢复和重试机制
LLM 集成模块应该处理 LLM API 调用失败或返回异常结果的情况。

#### Scenario: API 调用失败
- **WHEN** LLM API 请求失败（超时、网络错误等）
- **THEN** 系统应该自动重试，或降级到规则匹配方案

#### Scenario: 异常响应
- **WHEN** LLM 返回无法解析的响应
- **THEN** 系统应该记录日志，并返回用户友好的错误提示

### Requirement: LLM 提示词工程
LLM 集成模块应该使用精心设计的提示词，引导 LLM 做出正确的决策。

#### Scenario: 提示词设计
- **WHEN** LLM 集成模块调用 LLM API 时
- **THEN** 应该使用预设的提示词模板，清晰地说明任务目标、可用 Skill、期望的输出格式

#### Scenario: 上下文管理
- **WHEN** 提示词包含系统信息
- **THEN** 应该包含当前可用 Skill 的列表和描述，帮助 LLM 做出更准确的选择

### Requirement: LLM 深度思考模式集成
LLM 集成模块应该能够调用 LLM 的高级推理能力（如 Extended Thinking、Chain-of-Thought 等），用于深入理解复杂需求。

#### Scenario: 启用深度思考模式
- **WHEN** Agent 处理复杂、模糊或需要深度分析的需求时
- **THEN** 系统应该：
  1. 检测是否需要启用深度思考模式（可根据需求复杂度自动判断或由用户指定）
  2. 调用 LLM 的深度思考模式（如支持）
  3. 让 LLM 进行多步推理和分析

#### Scenario: 思考模式的应用场景
- **WHEN** 遇到以下情况时使用深度思考模式：
  - 用户需求模糊或有歧义
  - 需要理解修改的复杂意图
  - 需要生成高质量的修改建议
  - 需要分析修改对文档整体结构的影响
- **THEN** 系统应该启用深度思考模式进行分析

#### Scenario: 思考结果的使用
- **WHEN** LLM 深度思考完成后
- **THEN** 系统应该：
  1. 提取 LLM 的思考结论（而非仅思考过程）
  2. 基于思考结论生成具体的行动方案
  3. 选择性地向用户展示思考摘要

#### Scenario: 思考过程的透明性（可选）
- **WHEN** 用户想了解 Agent 的决策逻辑
- **THEN** 系统应该支持展示 LLM 思考的关键步骤：
  - "我首先理解了用户想要修改的三个方面..."
  - "这些修改之间的关系是..."
  - "我建议的修改顺序是..."
  - "预期的结果是..."

### Requirement: 多轮对话中的 LLM 上下文管理
LLM 集成模块应该在多轮对话中有效管理对话上下文，保持 LLM 对用户意图的连贯理解。

#### Scenario: 对话历史管理
- **WHEN** 用户进行多轮对话交互
- **THEN** 系统应该：
  1. 维护完整的对话历史（用户输入和 Agent 响应）
  2. 选择相关的历史信息传递给 LLM（避免超过 token 限制）
  3. 确保 LLM 能理解对话上下文

#### Scenario: 上下文压缩
- **WHEN** 对话轮数过多导致上下文过长
- **THEN** 系统应该：
  1. 总结之前的对话要点
  2. 保留关键的用户需求和反馈
  3. 将压缩后的上下文传递给 LLM

#### Scenario: 反馈的细化理解
- **WHEN** 用户对前一次的结果提供反馈或修正
- **THEN** LLM 应该：
  1. 在深度思考模式下理解反馈的具体含义
  2. 分析反馈涉及的具体修改点
  3. 评估修改对整体文档的影响
  4. 生成精准的修改方案

#### Scenario: 一致性保持
- **WHEN** 多轮修改过程中
- **THEN** 系统应该：
  1. 确保新修改不与之前确认的内容冲突
  2. 跟踪已确认和待确认的修改点
  3. 在 LLM 分析中保持对之前决策的考虑

### Requirement: LLM 提示词在多轮对话中的优化
提示词应该随着对话进行而动态优化，包含越来越多的上下文信息和用户偏好。

#### Scenario: 动态提示词构建
- **WHEN** Agent 与用户进行多轮对话
- **THEN** 提示词应该逐步积累：
  - 初始提示词：基础任务定义和 Skill 列表
  - 第一轮后：用户确认的需求和初步反馈
  - 后续轮次：已确认的内容、修改历史、用户偏好

#### Scenario: 用户风格学习
- **WHEN** 通过多轮对话
- **THEN** 系统应该学习用户的表达习惯和风格偏好，并在提示词中反映这些信息

#### Scenario: 修改模式识别
- **WHEN** 用户提供修改反馈
- **THEN** 系统应该：
  1. 识别用户的修改模式（关注的方面、优化方向）
  2. 在后续提示词中预先考虑这些倾向
  3. 提供更符合用户期望的修改建议
