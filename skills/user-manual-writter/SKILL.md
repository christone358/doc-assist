# User Manual Writter

## 聚焦范围

仅处理单个模块的用户使用手册编写或修订。

- 仅围绕一个目标模块组织内容，不扩写其他模块。
- 仅输出模块级第 4 章正文，不输出整本手册框架。
- 若用户要求整本手册、跨模块汇编或全系统用户指南，不使用本 skill 的正文结构；改为建议拆分为多个模块任务。

## 先读取哪些参考文件

在开始写作前，按以下顺序读取参考文件：

1. 读取 [references/structure/module-manual.md](references/structure/module-manual.md)，锁定模块级正文的唯一结构。
2. 读取 [references/rules/writing-rules.md](references/rules/writing-rules.md)，锁定写作规则、术语规则、缺口处理规则和风险提示规则。
3. 在完成初稿或修订稿后读取 [references/checklists/quality-checklist.md](references/checklists/quality-checklist.md)，执行自检。

不要在未读取结构参考文件时直接开始写作。不要自行发明新的章节树。

## 识别编写意图

在开始加载上下文前，先将任务归入以下三类之一：

### 1. `create`

适用于全新编写模块级第 4 章正文。

典型触发语义：

- “为 XXX 模块写用户手册”
- “全新编写 XXX 模块操作指南”
- “整理 XXX 模块终端用户使用说明”

### 2. `partial-update`

适用于只编写、补写或修订目标模块中的某一部分。

典型触发语义：

- “只补充 4.1.3 操作步骤”
- “完善导出子模块的异常处理”
- “只优化某个子模块的功能概述”

### 3. `revise-from-base`

适用于基于已有版本、历史保存稿或当前草稿做优化和改写。

典型触发语义：

- “基于当前版本优化”
- “按 v1.0 修改这部分”
- “在已有草稿基础上完善”

若同时出现“基于某版本”与“只改某一部分”，优先按 `revise-from-base` 处理，并在已有版本内执行局部修改。

## 规划事实加载

按“先模块定位、后理解用户意图和任务范围、再补事实细节”的顺序建立最小上下文。

### 必需事实

- 目标模块名称、模块职责、模块功能概述。
- 模块包含的主要子模块或用户任务。
- 每个相关子模块包括的功能项的具体描述。

### 通用加载顺序

若当前执行环境提供事实读取能力，按以下顺序建立上下文：

1. 先定位目标模块，确认是否唯一命中，以及对应的模块 ID、所属系统和所属子系统。
2. 若定位结果存在歧义或未找到，先向用户确认，不继续猜测或加载候选模块详情。
3. 在目标模块唯一明确后，再读取该模块相关的事实信息档案。了解这个模块事实档案中的模块描述、用例、子模块及其功能项、API接口信息。
4. 将模块事实主档视为当前阶段模块级写作的完整事实正文，直接基于其中的模块描述、用例、功能点、API、页面、依赖信息开展写作，不再为同一模块逐节重复加载功能描述或功能点详情。
5. 未来若系统引入源码、前端页面、原型页面等主档未覆盖的资源型事实入口，再按需补充读取。

### 运行时能力说明

本 skill 依赖以下运行时能力：

- 模块概览读取能力
- 用户场景或业务用例读取能力
- 界面或交互详情读取能力
- 当前草稿读取能力
- 历史版本读取能力

具体由哪些工具提供上述能力，取决于当前 agent 或系统的执行环境；本 skill 只规定所需能力和推荐顺序，不固定绑定具体工具名称。

### 分意图加载策略

#### `create`

- 不加载无关历史版本。
- 直接基于模块事实主档中的子模块清单、功能项和模块描述组织正文，不再逐个重复补拉同模块 section 详情。
- 若未来存在模块相关的资源型事实入口，可按需补充页面或实现细节；当前未提供这类资源时，不影响后续写作。
- 若缺少非关键细节，可保留缺口标记后继续写作。

#### `partial-update`

- 准确理解用户要求的修改章节、修改内容和修改意图。
- 定位用户明确指定的子模块、小节或编号范围。
- 只加载该局部相关事实，不因为局部任务扩写整个模块。按需加载功能页面原型信息。
- 若当前对话或历史保存稿中已有正文，读取和修改目标范围所需内容。

#### `revise-from-base`

- 必须先读取基线版本。基线可来自历史保存版本或当前对话草稿。
- 分析基线版本或草稿中，不满足用户要求的内容和差距。
- 识别影响范围，只补加载该范围所需的新事实。
- 未读取基线版本时，不应进入修订写作阶段。询问用户是否全新写作或终止写作。

### 事实不足时如何处理

- 缺少界面入口时，保留 `需确认界面路径`，不要编造菜单路径。
- 缺少字段明细时，仅写作事实信息中提到内容。保留 `待补充字段规则`，不要伪造取值约束。
- 缺少系统反馈时，保留 `待补充系统反馈文案`，不要杜撰提示语。
- 缺少截图时，保留 `截图待补充`，不要伪造图号或图注。

不要因为事实不完整而扩大加载范围到无关模块。只补与目标模块直接相关的事实。

## 执行流程

1. 确认任务属于单个模块范围。
2. 识别本次意图属于 `create`、`partial-update` 或 `revise-from-base`。
3. 锁定目标模块名称、目标读者和本轮改动范围。
4. 读取结构参考文件，确定唯一输出骨架。
5. 读取写作规则参考文件，确定正文写法和缺口处理方式。
6. 按“规划事实加载”章节中的对应策略加载事实或基线稿。
7. 输出模块级第 4 章正文或目标局部修订内容。
8. 读取质量检查清单，对结构、事实、步骤、术语、输出边界和改动范围做自检。
9. 仅在正文满足结构和质量要求后结束。

## 正文输出约束

- 只输出模块级手册正文。
- 不输出“编写说明”“事实来源说明”“执行摘要”“质量检查结论”到正文。
- 不输出思考过程、取数过程、判断过程或工具调用记录。
- 不把占位性说明扩写成额外章节。
- 不因用户未明确要求而增加其他模块、附录、全局概述或部署说明。
- 正文默认以 `## 4. 软件操作指南` 为起点，并在其下按子模块展开。

## 修订约束

- 先理解已有稿件的章节结构和编号体系。
- `partial-update` 与 `revise-from-base` 默认执行最小改动原则，不借机重写整章。
- 仅修改受影响的模块说明或子模块内容，不重写无关部分。
- 保持未受影响章节的标题、编号、术语和截图编号稳定。
- 若既有结构与 [references/structure/module-manual.md](references/structure/module-manual.md) 不一致，优先保持原文稳定，并只在受影响区域内按既有结构修订，除非用户明确要求重构。

## 交付目标

交付一份严肃、严格、专业的软件工程风格模块级第 4 章正文，使终端用户仅依赖该章节即可理解模块用途、完成标准操作、识别常见异常并规避高风险动作。
