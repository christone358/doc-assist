# 模块级用户使用手册写作规则

本文件定义 `user-manual-writter` 的写作规则。只规定写法，不规定新的章节结构。

## 1. 基本原则

- 坚持事实优先，所有内容必须基于已确认的项目事实。
- 坚持用户视角，只写终端用户可见、可执行、可验证的内容。
- 坚持边界清晰，不扩写目标模块之外的系统内容。
- 坚持专业表达，语气严肃、严格、克制，不使用宣传式或口语化表达。

## 2. 第 4 章与子模块写法

- `## 4. 软件操作指南` 用于对模块的具体使用方式进行说明。
- 每个 `### 4.x <模块名称>` 下按固定小节展开。
- 用 1 至 3 段说明当前子模块的职责、适用对象和业务用途。
- 说明“是什么”“给谁用”“解决什么问题”。
- 不写实现框架、类名、接口名、数据库表名或消息机制。

## 3. 子模块小节写法

### 3.1 功能概述

- 用 1 到 3 句话写清该子模块是什么、何时使用、完成后得到什么结果。
- 不写技术实现过程。

示例：
“新增用户功能用于创建系统访问账户。通过此功能，管理员可以为新入职人员分配登录账号和初始权限，使其能够访问授权范围内的系统功能。”

### 3.2 前置条件

- 只写用户在执行当前子模块操作前必须满足的条件。
- 优先覆盖权限、入口页面、业务对象状态、必要数据准备。
- 若入口不明确，写 `需确认界面路径`。

### 3.3 操作步骤

- 必须使用 `1. 2. 3.` 编号。
- 每一步只描述一个清晰动作。
- 动作必须可见、可执行、可复现。
- 先写进入页面，再按正常逻辑顺序写作，如输入、选择、确认、提交和结果回显。
- 分支处理，若有分支选项，分别描述（如“若选择A，则…；若选择B，则…”）
- 若字段规则缺失，写 `待补充字段规则`，不要伪造规则。
- 准确引用界面元素名称（如“点击【新增】按钮”），使用统一格式（如【】或加粗）标识
- 输入数据，说明必填项、数据格式要求（如“用户名：6-20位字母或数字”）

示例：
1. 在系统主界面左侧导航栏中，点击【用户管理】菜单，进入用户管理页面。
2. 点击页面右上角的【新增】按钮，弹出“新增用户”对话框（如图4-1所示）。
3. 填写以下信息：
   - 用户名：必填，6-20位字母或数字，不可重复
   - 登录口令：必填，长度≥8位，需包含大小写字母、数字、特殊字符中的至少三类
   - 姓名：必填，2-10个汉字
   - 角色：必选，从下拉列表中选择（管理员/操作员/观察员）
   - 部门：选填
4. 点击【确定】按钮提交。

### 3.4 输出/结果

- 写明成功提示、页面变化、数据变化和操作完成后的状态。
- 优先写用户直接可观察到的反馈。
- 若系统反馈缺失，写 `待补充系统反馈文案`。

示例：
**输出/结果**：
- 系统弹出“新增成功”提示（3秒后自动消失）。
- 用户列表自动刷新，新增用户显示在列表末尾，状态为“启用”。
- 页面返回用户管理主页，可对新增用户继续执行修改、禁用等操作。

### 3.5 异常处理

- 使用表格表达，列名固定为：`异常现象`、`可能原因`、`处理方法`。
- 仅覆盖用户高频可感知异常，不穷举技术内部异常。
- 处理方法必须是用户可执行动作，避免写“查看代码”“联系开发排查接口”之类的内部处理。

### 3.6 警告/注意

- 仅在删除、禁用、权限变更、覆盖导入、批量执行、不可逆提交等高风险场景下仅在高风险场景下使用。
- 必须写清风险对象、影响后果和用户应采取的确认动作。

示例：删除用户操作不可恢复，该用户的所有历史数据将被标记为“已删除用户”，请谨慎操作。


## 4. 界面元素命名规则

### 4.1 界面元素引用规范
统一使用以下格式：

| 元素类型 | 写法 | 示例 |
| --- | --- | --- |
| 按钮 | `【按钮名称】` | 点击【保存】按钮 |
| 菜单 | `【菜单】>【子菜单】` | 选择【系统管理】>【用户管理】 |
| 选项卡 | `“选项卡名称”` | 切换到“基本信息”选项卡 |
| 输入框 | `“字段名称”输入框` | 在“用户名”输入框中输入 |
| 对话框 | `“对话框名称”对话框` | 弹出“新增用户”对话框 |
| 下拉框 | `“字段名称”下拉框` | 在“状态”下拉框中选择“启用” |

同一对象在全文中只允许一种称呼，不混用近义词。

### 4.2 语言要求
- 使用主动语态，使用主语+动词结构，明确动作执行者，如“点击【新增】按钮”
- 使用祈使句，直接告诉用户做什么，如“输入用户名”；
- 避免技术术语，用用户能理解的语言，如“点击【确定】保存设置”，而不是“调用POST接口提交数据”；
- 保持一致术语，同一概念全文档用统一名称，如：始终用“用户”而非混用“用户/账号/账户”，而非同一文档中“用户/账号/账户”混用。
- 优先使用短句，避免口号式、营销式和模糊性表达。

## 5. 缺口处理规则

当事实不完整时，允许保留明确缺口，但禁止伪造。

统一使用以下标记：

- `需确认界面路径`
- `待补充字段规则`
- `待补充系统反馈文案`
- `截图待补充`
- `需产品确认`

缺口标记应嵌入相关段落，不要单独扩成“待确认项说明”章节。

## 6. 禁止事项

- 禁止编造按钮名、字段名、提示文案、异常场景或权限规则。
- 禁止写“调用接口”“写入数据库”“触发任务”“同步缓存”等实现术语。
- 禁止输出分析说明、事实来源说明、质量检查结论到正文。
- 禁止把多个操作目标合并成一个子模块。
- 禁止把管理规范、部署要求、开发约束写入用户操作手册正文。
