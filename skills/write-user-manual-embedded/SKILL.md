# 软件用户使用手册编写

编写或修订面向最终用户的软件使用手册，重点生成第 4 章“软件操作指南”。

## Core Workflow

1. 确定写作目标与交付范围。
- 识别当前任务是全新编写手册、补写某一章节，还是修订现有版本。
- 提取目标系统、目标模块的草稿或已有历史版本文档。

2. 定位事实材料并建立最小上下文。
- 优先读取项目事实信息中能支撑用户数册编写的资料：功能描述、模块和子模块信息、子模块的具体功能项，关联页面的信息元素、交互等。
- 如果事实材料不足以支撑正式写作，不编造界面、按钮、字段、提示语或异常场景；用 `待补充`、`需确认` 明示缺口。

3. 明确用户手册章节结构。
- 严格按照 ## Chapter 4 写作标准 中规定的章节骨架结构进行编写。不得修改结构。
- 禁止编写全量版本、全部功能模块使用手册，每次聚焦一个功能模块。当任务由多个功能模块构成时，也应该按顺序分别处理。
- 为每个模块的编写需要覆盖所有子模块和功能项信息，避免遗漏功能点。

4. 编写第 4 章“软件操作指南”。
- 每个最小操作单元默认使用以下结构：
  - `功能概述`
  - `前置条件`
  - `操作步骤`
  - `输出/结果`
  - `异常处理`
  - `警告/注意`（仅在存在安全、权限、删除、停用、覆盖等风险时添加）


5. 修订既有手册时控制改动范围。
- 先读历史版本，再识别本次变更影响的模块、步骤、截图、术语和章节编号。
- 只修改受影响段落，不为统一文风而重写整章。
- 保持未受影响章节的编号、路径名称、截图编号和术语稳定。

## 事实信息加载说明

应加载模块档案信息和相关页面原型，以全面了解写作目标模块的全部知识。

如果某项内容只能从实现细节中推断，而用户可见事实缺失，将其写成 `实现现状待确认` 或 `需产品确认`，不要直接上升为正式手册内容。

## Chapter 4 章节结构

第 4 章默认采用以下层级：

```text
4. 软件操作指南
  4.1 <模块名称>
    4.1.1 <操作名称>
      4.1.1.1 功能概述
      4.1.1.2 操作步骤
      4.1.1.3 输出/结果
      4.1.1.4 异常处理
```

执行规则：
- 优先按功能模块划分章节，保证功能边界清晰。
- 二级标题对应写作目标模块；
- 三级标题对应写作目标中的子模块，作为最小操作单元；子模块中的全部功能项，都应写入。
- 每个操作单元应包含章节模板要求的全部结构，四级标题下即使没有正文可写，也要保持标题存在。内容写：无。
- 同一模块下的操作单元按用户常用频率或自然流程排序。

示例：
章节结构和层级：

```text
4. 软件操作指南
  4.1 用户管理模块
    4.1.1 用户登录
      4.1.1.1 功能概述
      4.1.1.2 操作步骤
      4.1.1.3 输出/结果
      4.1.1.4 异常处理
    4.1.2 新增用户
      4.1.1.1 功能概述
      4.1.1.2 操作步骤
      4.1.1.3 输出/结果
      4.1.1.4 异常处理
  4.2 数据管理模块
    4.2.1 数据导入
      4.1.1.1 功能概述
      4.1.1.2 操作步骤
      4.1.1.3 输出/结果
      4.1.1.4 异常处理
```

## 详细写作规则

### 1. 章节组织

严格按照 ## Chapter 4 章节结构 中要求的目标结构组织。


### 2. 最小操作单元结构

子模块作为最小操作单元结构。子模块下的所有功能项都应被描述到改操作单元内。

#### 2.1 功能概述

要求：
- 说明该功能是什么，以及为什么使用。
- 篇幅控制在 1 到 3 句话。
- 使用用户视角语言，不写实现机制。

示例：

```markdown
新增用户功能用于创建系统访问账户。通过此功能，管理员可以为新入职人员分配登录账号和初始权限，使其能够访问授权范围内的系统功能。
```

#### 2.2 操作步骤

要求：
- 按顺序编号，使用 `1. 2. 3.` 格式。
- 每一步只写一个明确动作。
- 在步骤前单独说明前置条件。
- 界面元素名称必须与实际界面一致。
- 必填项、格式要求、长度限制、取值范围必须写清楚。
- 存在分支时分别说明。

写作示例：

```markdown
**前置条件**：
- 当前登录账号具有“用户管理”权限。
- 已进入“用户管理”页面（操作路径：【系统管理】>【用户管理】）。

**操作步骤**：
1. 在“用户管理”页面，点击页面右上角的【新增】按钮。
2. 系统弹出“新增用户”对话框（如图 4-2 所示）。
3. 填写用户信息：
   - 用户名：必填，6-20 位字母或数字，不可重复。
   - 登录口令：必填，长度不少于 8 位，且至少包含三类字符。
   - 角色：必选，从下拉列表中选择。
4. 点击【确定】按钮提交。
5. 系统校验通过后完成新增。
```

#### 2.3 输出/结果

要求：
- 描述正常情况下的提示信息、页面变化、数据变化和后续状态。
- 尽量写出用户直接可见的系统反馈。

示例：

```markdown
**输出/结果**：
- 系统弹出“新增成功”提示，3 秒后自动消失。
- 对话框自动关闭，页面返回“用户管理”列表。
- 用户列表自动刷新，新增用户显示在列表中，状态为“启用”。
```

#### 2.4 异常处理

要求：
- 优先列常见异常和高频错误，不追求穷尽所有技术异常。
- 写清楚异常现象、可能原因和处理方法。
- 使用表格表达。

推荐表头：

| 异常现象 | 可能原因 | 处理方法 |
| --- | --- | --- |
| 提示“用户名已存在” | 用户名已被占用 | 更换用户名后重新提交 |

### 3. 语言规范

#### 3.1 行文风格

- 使用祈使句和主动语态，例如“点击【确定】按钮”“在‘用户名’输入框中输入”。
- 不使用实现术语，例如“调用接口”“提交 POST 请求”“写入数据库”。
- 保持术语一致；同一对象在全文中固定一种称呼，不混用“用户/账号/账户”等近义词。
- 使用主动语态，例如“点击【保存】按钮”。
- 不使用模糊表达，如“适当调整”“快速完成”“系统自动处理相关逻辑”。

#### 3.2 术语一致性

- 同一对象全文只用一个名称。
- 菜单名、按钮名、字段名、对话框名必须与界面一致。
- 如果产品中确有两个近义对象，例如“用户”和“账户”，先给出定义，再固定使用。

### 4. 界面元素引用规范
- 严格使用以下界面元素写法：

| 元素类型 | 引用格式 | 示例 |
| --- | --- | --- |
| 按钮 | 【按钮名称】 | 点击【确定】按钮 |
| 菜单 | 【菜单项】>【子菜单】 | 选择【系统管理】>【用户管理】 |
| 选项卡 | “选项卡名称” | 切换到“基本信息”选项卡 |
| 输入框 | “字段名称”输入框 | 在“用户名”输入框中输入 |
| 对话框 | “对话框名称”对话框 | 弹出“新增用户”对话框 |
| 快捷键 | `<键名>+<键名>` | 按 `<Ctrl>+<S>` 保存 |

### 5. 警告与注意事项

涉及以下操作时应写入到警告与注意事项中呢：
- 删除
- 禁用
- 权限变更
- 覆盖导入
- 批量执行
- 数据提交后不可撤回

推荐格式：

```markdown
**警告**：删除用户操作不可恢复，请谨慎执行。
```

```markdown
**注意**：禁用用户后，该用户将立即无法登录系统，正在进行的任务可能被中断。
```

写法要求：
- 写清楚风险对象。
- 写清楚影响结果。
- 写清楚用户应采取的确认动作或规避方法。

## 写作规则

- 使用面向用户的语言，默认读者为业务用户、管理员或操作员，而不是开发人员。
- 每条步骤都应包含明确动作对象，如菜单、按钮、选项卡、输入框或对话框。
- 输入项需要说明是否必填、格式限制、枚举值、长度限制或唯一性要求。
- 分支操作需要显式写出条件，例如“若选择 A，则……；若选择 B，则……”。
- 成功结果需要写明提示信息、页面变化、数据变化和后续可执行动作。
- 异常处理表格至少包含：异常现象、可能原因、处理方法。
- 遇到删除、导入覆盖、权限停用、批量执行等操作时，必须写警告或注意事项。
- 优先写用户可直接观察到的现象，避免写数据库、接口、线程、缓存等实现细节。
- 全文保持同一术语、同一按钮命名、同一截图编号体系。
- 如果存在未知字段、未知校验或未知提示文案，保留待确认标记，不编造示例值冒充真实规则。
