# 软件用户使用手册编写

编写或修订面向最终用户的软件使用手册，重点生成第 4 章“软件操作指南”。按功能模块组织章节，按最小操作单元展开说明，并在完成后检查步骤可复现性、界面名称一致性、异常处理充分性和安全提示完整性。

## 编写用户手册的事实信息加载说明

按“先用户可见信息、后实现支撑；先范围、后细节”的顺序读取材料。

| 写作目标 | 先读取 | 按需追加 |
| --- | --- | --- |
| 编写功能概述 | 模块功能说明、需求文档 | 页面原型 |
| 编写操作步骤 | 菜单结构、原型、页面截图、测试步骤 | 前端页面、交互说明、录屏描述 |
| 编写输入要求 | 表单字段说明、校验规则、页面文案 | 接口契约、测试数据约束 |
| 编写输出结果 | 成功提示、列表刷新行为、状态变化说明 | 测试结果、页面说明 |
| 编写异常处理 | 错误提示、失败场景、权限说明 | 常见问题、测试异常用例、日志样例 |
| 编写警告提示 | 安全要求、权限说明、业务规则 | 审计要求、操作限制 |
| 修订既有文档 | 历史手册、变更点说明 | 受影响页面或截图 |

如果某项内容只能从实现细节中推断，而用户可见事实缺失，将其写成 `实现现状待确认` 或 `需产品确认`，不要直接上升为正式手册内容。

**推荐加载顺序**：
- 先调用 `get_fact_overview("modules")` 定位目标模块名称和模块 ID。
- 若任务是围绕某个模块编写用户手册，再调用 `get_fact_overview("usecases")` 补充该模块相关的用户操作场景。
- 若存在接口或原型事实，再按需调用 `get_fact_detail(target_id, "interfaces")` 或 `get_fact_detail(target_id, "prototypes")`。
- 如果已经能定位目标模块且掌握其核心职责、关键特性和相关用例，就应开始写作；缺少截图、原型或页面文案时，保留 `待确认` 标记，而不是立刻向用户追问。

## Core Workflow

1. 确定写作目标与交付范围。
- 识别当前任务是全新编写手册、补写某一章节，还是修订现有版本。
- 提取目标系统、目标模块、目标读者、输出语言和期望交付范围。
- 将“用户手册”“操作手册”“软件操作指南”“终端用户手册”“使用说明书”视为本 skill 的主要触发语义。
- 如果用户只要求编写某个功能或某一章，保持范围收敛，不扩写其他章节。

2. 定位事实材料并建立最小上下文。
- 优先读取用户明确提供的材料：现有手册、原型、页面截图、菜单结构、需求文档、培训材料、测试步骤、产品说明、发布说明。
- 将页面原型、前端页面、接口说明、测试用例都视为候选事实源，但只按需读取。
- 优先读取能支撑用户视角操作的材料：菜单层级、字段定义、按钮名称、提示文案、错误提示、权限说明、风险提示。
- 如果事实材料不足以支撑正式写作，不编造界面、按钮、字段、提示语或异常场景；用 `待补充`、`需确认` 明示缺口。

3. 规划手册结构。
- 第 4 章默认按“功能模块”组织，除非用户明确要求按业务场景或角色任务组织。
-  每个模块的写作章节按照[templates/operation-unit-template.md](templates/peration-unit-template.md)。
- 为每个模块先列出操作单元清单，再开始逐个编写正文，避免遗漏功能点。

4. 为每个最小操作单元收集必需事实。
- 在正式落笔前确认以下事实是否存在：功能用途、前置条件、操作入口、关键按钮/菜单名称、输入项与格式要求、成功反馈、常见异常、风险提示。
- 如果缺少“操作入口”或“界面元素名称”，不要输出正式步骤；先标记 `需确认界面路径`。
- 如果缺少“成功反馈”或“异常提示”，可先写出已确认结果，并显式标注 `待补充系统反馈文案`。
- 如果存在截图编号或页面原型，记录其与步骤的映射关系，保证图文一致。

5. 编写第 4 章“软件操作指南”。
- 每个最小操作单元默认使用以下结构：
  - `功能概述`
  - `前置条件`
  - `操作步骤`
  - `输出/结果`
  - `异常处理`
  - `警告/注意`（仅在存在安全、权限、删除、停用、覆盖等风险时添加）
- 使用 [templates/operation-unit-template.md](templates/operation-unit-template.md) 作为操作单元骨架。
- 功能概述只写“是什么”和“为什么用”，保持 1 到 3 句话，面向用户，不引入实现术语。
- 操作步骤按时间顺序编号；每一步只描述一次动作，动作要可见、可执行、可复现。
- 输出/结果同时说明界面反馈、数据变化和后续状态。
- 异常处理优先用表格列出：异常现象、可能原因、处理方法。

6. 统一语言与界面引用。
- 使用祈使句和主动语态，例如“点击【确定】按钮”“在‘用户名’输入框中输入”。
- 不使用实现术语，例如“调用接口”“提交 POST 请求”“写入数据库”。
- 保持术语一致；同一对象在全文中固定一种称呼，不混用“用户/账号/账户”等近义词。
- 严格使用以下界面元素写法：

| 元素类型 | 引用格式 | 示例 |
| --- | --- | --- |
| 按钮 | `【按钮名称】` | 点击【保存】按钮 |
| 菜单 | `【菜单】>【子菜单】` | 选择【系统管理】>【用户管理】 |
| 选项卡 | `“选项卡名称”` | 切换到“基本信息”选项卡 |
| 输入框 | `“字段名称”输入框` | 在“用户名”输入框中输入 |
| 对话框 | `“对话框名称”对话框` | 弹出“新增用户”对话框 |
| 快捷键 | `<键名>+<键名>` | 按 `<Ctrl>+<S>` 保存 |

7. 处理高风险操作提示。
- 涉及删除、禁用、权限变更、数据覆盖、批量提交、导入导出、不可恢复动作时，补充醒目标识。
- 优先使用以下两种格式：

```markdown
**警告**：删除操作不可恢复，请确认后再执行。
```

```markdown
**注意**：禁用用户后，该用户将立即无法登录系统。
```

- 警告内容必须具体写明风险对象、影响范围和用户应采取的确认动作。

8. 修订既有手册时控制改动范围。
- 先读历史版本，再识别本次变更影响的模块、步骤、截图、术语和章节编号。
- 只修改受影响段落，不为统一文风而重写整章。
- 保持未受影响章节的编号、路径名称、截图编号和术语稳定。
- 如果界面已经变化但历史截图未更新，明确标记 `截图待更新`，不要假装图文一致。

9. 完成后执行质量检查。
- 按 [references/quality-checklist.md](references/quality-checklist.md) 检查结构、覆盖、步骤、术语、异常、截图和警告。
- 对确定性问题直接修正后复查。
- 对无法确认的问题保留明确待确认项，不用经验补全。
- 在最终输出中附上简短检查结论，说明通过项、待确认项和主要事实来源。



## Chapter 4 写作标准

第 4 章默认采用以下层级：

```text
4. 软件操作指南
  4.1 <模块名称>
    4.1.1 <操作名称>
      4.1.1.1 功能概述
      4.1.1.2 操作步骤
      4.1.1.3 输出/结果
      4.1.1.4 异常处理
```

执行规则：
- 优先按功能模块划分章节，保证功能边界清晰。
- 同一模块下的操作单元按用户常用频率或自然流程排序。
- 如果模块过大，先拆子模块，再写操作单元，但总层级仍不超过三级。
- 每个操作单元至少包含 `功能概述`、`操作步骤`、`输出/结果`、`异常处理` 四部分；前置条件可单独列出。
- 关键界面步骤应引用截图编号，如“如图 4-1 所示”；图号必须与图注一致。

## 写作规则

- 使用面向用户的语言，默认读者为业务用户、管理员或操作员，而不是开发人员。
- 每条步骤都应包含明确动作对象，如菜单、按钮、选项卡、输入框或对话框。
- 输入项需要说明是否必填、格式限制、枚举值、长度限制或唯一性要求。
- 分支操作需要显式写出条件，例如“若选择 A，则……；若选择 B，则……”。
- 成功结果需要写明提示信息、页面变化、数据变化和后续可执行动作。
- 异常处理表格至少包含：异常现象、可能原因、处理方法。
- 遇到删除、导入覆盖、权限停用、批量执行等操作时，必须写警告或注意事项。
- 优先写用户可直接观察到的现象，避免写数据库、接口、线程、缓存等实现细节。
- 全文保持同一术语、同一按钮命名、同一截图编号体系。
- 如果存在未知字段、未知校验或未知提示文案，保留待确认标记，不编造示例值冒充真实规则。

## Output Expectations

默认交付应包含：
- 一份完整的用户使用手册，或指定章节/模块的增量修订内容。
- 对于第 4 章中的每个操作单元，给出完整结构化说明。
- 一段简短事实来源说明，概括本次实际读取的材料类型。
- 一份简短质量检查结论，说明结构完整性、可操作性和待确认项。

## Arguments

可选使用以下参数组织任务；如果用户未显式提供，也可根据自然语言意图推断：

```text
$ARGUMENTS: <系统/模块/任务目标> [--scope full|chapter4|module] [--base <现有手册路径>] [--audience <读者>] [--output <输出路径>]
```

参数说明：
- `<系统/模块/任务目标>`：必需，说明要写哪个系统、模块或操作主题。
- `--scope`：可选，`full` 表示完整手册，`chapter4` 表示只写第 4 章，`module` 表示只写一个或多个模块。
- `--base`：可选，用于修订现有手册。
- `--audience`：可选，用于指定读者，如管理员、业务人员、审核人员。
- `--output`：可选，用于指定输出文档路径。

示例：

```text
编写采购管理系统用户使用手册 --scope full
编写用户管理模块的软件操作指南 --scope module
更新库存系统第4章操作手册 --scope chapter4 --base docs/manuals/inventory-user-manual.md
为管理员角色编写权限管理操作手册 --scope module --audience 管理员
```
