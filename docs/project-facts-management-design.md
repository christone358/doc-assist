# 项目事实信息管理方案设计

## 文档信息
- 文档名称: 项目事实信息管理方案设计
- 版本: v1.0.0
- 创建日期: 2026-04-01
- 作者: Codex
- 适用范围: NextAgent Doc Assistant 项目事实信息建设与管理

## 1. 背景

当前项目事实信息曾长期并行存在多种表达方式：

- 根目录聚合 Markdown
- 结构化 JSON 导入产物
- 零散的说明性文档

这些表达方式分别适合 Agent 读取、批量加工或人工说明，但缺少唯一事实源，导致以下问题：

- 用户不知道应该维护哪一层
- 同一事实在多处重复维护，容易不一致
- 模块变更后很难快速同步到 Agent、页面和导入结果
- 原型、接口、类包等关联信息不易在一个地方查看

因此需要建立一套易于用户维护、易于 Agent 读取、能够逐步沉淀的项目事实信息管理方案。

## 2. 设计目标

### 2.1 目标

- 建立唯一的人工维护标准，避免多套事实源并存
- 以模块为中心组织事实信息，支持渐进式补充
- 降低用户维护成本，不要求手工维护机器 ID
- 支持 Markdown 手工维护与 Excel 导入
- 支持 Agent 按模块稳定读取上下文
- 支持 Web UI 以模块视角浏览已维护事实信息
- 支持 Axure 原型整包集中存放，并通过页面名称与模块关联

### 2.2 非目标

- 本期不建设完整知识图谱数据库
- 本期不要求 UI/数据库直接写回模块档案
- 本期不实现自动页面摘要生成
- 本期不实现完整度评分
- 本期不要求细粒度类依赖、页面调用链等双向关系维护

## 3. 核心设计原则

### 3.1 模块档案是唯一人工维护单元

每个模块对应一份模块档案，产品、研发和后续维护人员都围绕同一份文档持续补充信息。

### 3.2 自然语言优先，机器标识自动派生

用户维护模块名称、功能描述、功能点、页面名称、API 名称、类名等自然语言内容。内部标识、索引和关系由系统自动生成。

### 3.3 人工维护层与系统派生层分离

- 人工维护层: `project-facts/modules/*.md`
- 系统派生层: `project-facts/generated/*`

派生层只用于检索、加载和展示，不作为权威事实源。

### 3.4 关系以模块聚合为主

模块档案主维护以下信息：

- 功能描述
- 功能点
- API 清单
- 页面 / 原型
- 包 / 类
- 依赖模块

系统默认将这些内容解释为模块与下属事实的关联关系。

## 4. 总体架构

```text
用户维护入口
├─ Markdown 模块档案
├─ Excel 导入
└─ 原型整包投放

        ↓

唯一事实源
└─ project-facts/modules/*.md

        ↓ 系统解析与派生

派生层
├─ generated/module-index.json
├─ generated/module-id-map.json
├─ generated/relation-index.json
├─ generated/views/modules.md
└─ prototypes/page-index.json

        ↓

消费层
├─ Agent 上下文加载
├─ 事实信息浏览页面
└─ 检索与查询接口
```

## 5. 目录结构设计

```text
project-facts/
├─ README.md
├─ modules/                        # 唯一人工维护层
│  ├─ 模块档案模板.md
│  ├─ 云主机资产管理.md
│  └─ ...
├─ prototypes/                     # 原型集中存放
│  ├─ axure-export/
│  │  ├─ index.html
│  │  └─ ...
│  └─ page-index.json             # 系统生成
└─ generated/                      # 系统派生层
   ├─ module-index.json
   ├─ module-id-map.json
   ├─ relation-index.json
   └─ views/
      ├─ modules.md
      └─ module-details/
```

研发过程的方案说明、验收清单和设计讨论文档统一放在 `docs/` 目录，不放入 `doc_output/`。

## 6. 模块档案标准

模块档案采用固定骨架，降低维护成本并提升解析稳定性。

标准结构如下：

```markdown
# 云主机资产管理

## 基本信息
- 所属系统: 业务保障管理系统
- 模块状态: active
- 别名: 云主机管理

## 功能描述
面向资产管理员，提供云资源自动化同步监控能力，实现混合云环境统一纳管目标。

## 功能点
| 功能点 | 描述 | 状态 |
|---|---|---|
| 云服务资产列表 | 设备资产查询 | 已完成 |

## API 清单
| API 名称 | 说明 | 路径 | 方法 |
|---|---|---|---|

## 页面 / 原型
- 云主机列表页
- 云主机详情页

## 包 / 类
- CloudHostService

## 依赖模块
- 监控中心

## 备注
待补充
```

### 6.1 章节含义

- `基本信息`: 系统归属、状态、别名
- `功能描述`: 模块职责与业务价值
- `功能点`: 用户可见或业务可理解的能力点
- `API 清单`: 模块对外暴露接口
- `页面 / 原型`: 模块关联页面名称
- `包 / 类`: 研发补充的实现视角信息
- `依赖模块`: 跨模块依赖
- `备注`: 特殊说明、限制与迁移备注

### 6.2 维护特点

- 允许信息不完整
- 允许先写业务信息、后补技术信息
- 不要求用户维护 `mod-xxx` 之类的内部标识

## 7. 派生索引设计

系统从模块档案生成以下索引。

### 7.1 模块索引

文件: `generated/module-index.json`

作用：

- 提供模块列表
- 支撑搜索和筛选
- 供前端模块浏览页使用

### 7.2 稳定 ID 映射

文件: `generated/module-id-map.json`

作用：

- 为每个模块分配稳定内部 ID
- 记录模块标题、别名和文件路径映射
- 在模块改名时保留历史检索能力

### 7.3 关系索引

文件: `generated/relation-index.json`

作用：

- 记录模块与功能点、API、页面、包 / 类、依赖模块之间的关系
- 供 Agent 与查询接口使用

### 7.4 聚合视图

文件:

- `generated/views/modules.md`
- `generated/views/module-details/*.md`

作用：

- 为 Agent 和调试提供可读视图
- 在不直接读取原始模块档案时提供缓存化上下文

## 8. 原型管理方案

### 8.1 存放原则

Axure 导出的原型通常是整包 HTML 资源，因此不要求按模块拆分。

统一存放方式：

```text
project-facts/prototypes/
└─ axure-export/
   ├─ index.html
   ├─ 页面A.html
   └─ 页面B.html
```

### 8.2 模块关联方式

模块档案中只维护页面名称：

```markdown
## 页面 / 原型
- 云主机列表页
- 云主机详情页
```

系统扫描 `prototypes/` 中的 HTML 文件，并生成 `page-index.json`，实现页面名称到原型文件路径的匹配。

### 8.3 当前边界

- 当前支持页面名称匹配与路径展示
- 当前不自动生成页面摘要
- 若后续需要支持用户手册、需求规格对页面布局的深入理解，应单独建设页面摘要工具

## 9. Excel 导入方案

### 9.1 目标

支持从 Excel 批量导入模块信息，但最终仍写回模块档案。

### 9.2 当前导入口径

以 `资产功能规划.xlsx` 为例，当前导入规则为：

- `二级功能` → 模块
- `二级功能描述` → 模块描述
- `三级功能 + 功能点` → 模块中的功能点

### 9.3 字段映射

| Excel 字段 | 模块档案位置 |
|---|---|
| 系统名称 | 基本信息 / 所属系统 |
| 二级功能 | 模块标题 |
| 二级功能描述 | 功能描述 |
| 三级功能 | 功能点 |
| 功能点 | 功能点描述 |
| 完成状态 | 功能点状态 |
| 备注列 | 备注 |

### 9.4 导入行为

- 导入前清理目标系统下的旧业务模块档案
- 根据新口径生成模块档案
- 同步刷新 `generated/` 目录索引

## 10. Agent 读取方案

### 10.1 读取原则

Agent 优先从模块档案及其派生视图读取上下文，而不再依赖旧的全局总表标签过滤。

### 10.2 当前加载链路

- 模块总览: `generated/views/modules.md`
- 类 / 包详情: 模块详情视图中的 `包 / 类` 章节
- 接口详情: 模块详情视图中的 `API 清单` 章节
- 原型详情: 模块详情视图中的 `页面 / 原型` 章节

### 10.3 模块定位方式

- 先按模块名称匹配
- 再按别名匹配
- 模块内部 ID 只供系统使用

## 11. Web UI 浏览方案

### 11.1 浏览视图

项目事实信息页面采用模块浏览器模式：

- 左侧: 模块列表
- 右侧: 模块详情

### 11.2 当前展示内容

右侧模块详情面板展示：

- 功能描述
- 功能点
- API 清单
- 页面 / 原型
- 包 / 类
- 依赖模块
- 备注

### 11.3 设计取向

- 重点展示右侧模块事实内容
- 左侧模块列表保持纵向滚动
- 浏览视角与维护视角一致

## 12. 持久化与路径约定

为避免服务从不同工作目录启动时读到错误位置，所有关键目录都应基于仓库根目录解析：

- `project-facts/`
- `doc_output/`
- `backend/docs/conversations/`
- `skills/`

这是当前实现里非常关键的一条工程约束。

## 13. 运行与维护流程

### 13.1 新增模块

1. 复制模块档案模板
2. 填写模块名称、功能描述和功能点
3. 后续补充 API、页面、包 / 类和依赖模块
4. 刷新派生索引

### 13.2 Excel 导入

1. 准备源 Excel
2. 执行导入脚本
3. 检查 `project-facts/modules/` 中生成的模块档案
4. 检查 `generated/` 中的索引和视图
5. 在 UI 中查看展示结果

### 13.3 原型更新

1. 将原型整包放入 `project-facts/prototypes/`
2. 在模块档案中维护页面名称
3. 刷新页面索引

## 14. 当前实现状态

当前已落地：

- 模块档案标准
- 模块档案解析器
- 稳定 ID 映射
- 模块关系索引
- 原型页面名称索引
- Excel 导入到模块档案
- Agent 模块视角加载
- Web UI 模块浏览页

当前未落地：

- 自动页面摘要生成
- UI 直接编辑并写回模块档案
- 完整度评分
- 更细粒度实体关系维护

## 15. 后续演进建议

### 15.1 页面摘要工具

单独建设原型页面摘要生成工具，用于支撑用户手册、需求规格等页面级文档编写。

### 15.2 模块档案编辑器

在 UI 中增加模块档案编辑能力，但底层仍写回 Markdown。

### 15.3 更丰富的关系分析

在保证维护成本可控的前提下，逐步增加：

- 模块依赖分析
- 页面到接口关系
- 接口到实现类关系

## 16. 结论

本方案以“模块档案”作为唯一人工维护单元，用自然语言维护、系统自动派生索引和关系，兼顾了用户维护成本、Agent 可读性和工程可持续性。

对于当前项目阶段，这是一套足够简单、同时又能支撑后续扩展的项目事实信息管理方案。
