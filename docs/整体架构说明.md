# NextAgent Doc Assistant 整体架构说明

## 文档信息
- 文档名称: NextAgent Doc Assistant 整体架构说明
- 版本: v1.0.0
- 创建日期: 2026-04-10
- 适用范围: 当前仓库实现的整体架构、核心组成、关键链路与主要设计决策

## 1. 文档目标

本文档用于说明本项目当前的整体架构，重点回答以下问题：

- 系统由哪些核心组成部分构成
- 项目知识管理、MCP server、Agent、Skill、LLM 之间如何协作
- 主 Agent 与子 Agent 分别负责什么
- 为什么项目知识管理采用“以模块为聚合根”的方式
- 为什么采用主子 Agent 隔离来解决上下文与职责边界问题

本文档关注的是“系统如何组织与运行”，不是某个单点模块的详细设计说明。知识库维护细则、MCP 协议细节、LLM 配置细则分别在已有专题文档中展开。

## 2. 系统定位

NextAgent Doc Assistant 是一个面向软件工程文档生产的 Agent 系统。它不是单纯的“聊天 + 大模型”，而是围绕“工程事实驱动的文档生成”构建的多层架构：

- 前端负责交互、展示和可观测性
- 后端负责会话管理、Agent 编排、文档版本管理和项目事实查询
- 主 Agent 负责理解用户意图、选择 Skill、调度子 Agent
- Skill 子 Agent 负责具体写作执行
- MCP Runtime 负责为 Agent 提供统一的运行时资源访问能力
- 项目知识库为文档写作提供可维护、可检索、可追溯的事实依据
- LLM 负责推理、编排判断和内容生成

它的核心目标不是“让模型自由发挥”，而是让模型在明确的资源边界、职责边界和事实边界中稳定工作。

## 3. 总体架构全景

```text
用户
  |
  v
前端 Web UI（Svelte）
  |- 对话界面
  |- Skill 展示
  |- 项目事实浏览
  |- LLM 配置
  |- 执行过程可观测面板
  |
  v
后端 API / WebSocket（FastAPI）
  |- 会话管理
  |- Agent 运行入口
  |- 文档版本管理
  |- 项目事实接口
  |- LLM 配置接口
  |
  v
主 Agent / Orchestrator
  |- 意图识别
  |- 查询与写作分流
  |- Skill 选择
  |- 子 Agent 调度
  |
  +----------------------------+
  |                            |
  v                            v
MCP Runtime                Skill Sub-agent
  |- facts.*                  |- 读取当前草稿
  |- prototypes.*             |- 加载模块事实
  |- docs.*                   |- 加载历史文档
  |- artifacts.*              |- 读取 Skill 资源
                              |- 调用写作工具生成正文
  |                            |
  +------------+---------------+
               |
               v
      运行时资源与持久化数据
      |- project-facts/      项目知识库
      |- skills/             Skill 定义与私有资源
      |- doc_output/         正式文档版本
      |- backend/docs/...    会话日志
      |- llm_configs.json    LLM 配置
```

从职责上看，系统可以分为四层：

1. 交互层：前端页面与 WebSocket 流式交互。
2. 编排层：主 Agent 负责“判断做什么”。
3. 执行层：Skill 子 Agent 负责“具体怎么做”。
4. 资源层：项目知识库、Skill 资源、历史文档、原型、LLM 配置等。

## 4. 核心组成部分

## 4.1 前端

前端位于 `frontend/`，基于 Svelte 实现，主要承担以下职责：

- 提供对话入口
- 通过 REST API 管理会话、Skill、文档和事实信息
- 通过 WebSocket 接收流式回复和执行状态
- 展示子 Agent 的执行过程、工具调用和中间状态
- 提供 LLM 配置管理界面

前端不是业务逻辑中心，它主要是后端 Agent 系统的交互壳和观察窗口。

## 4.2 后端 API 与会话管理

后端位于 `backend/`，以 FastAPI 为入口，主要职责包括：

- 提供 REST API 和 WebSocket 接口
- 创建和持久化对话会话
- 驱动 Agent 执行链路
- 管理文档保存、历史版本读取和版本查询
- 提供项目事实信息查询接口
- 提供 LLM 配置管理接口

其中会话管理是系统连续对话能力的基础：

- 会话元数据和轮次记录保存在 `backend/docs/conversations/`
- 对话中的草稿状态、执行摘要、执行事件会随轮次一起沉淀
- 主 Agent 依赖这些状态维持多轮写作的连续性

## 4.3 主 Agent / Orchestrator

主 Agent 是整个系统的编排中枢。它并不直接承担完整写作，而是负责以下事项：

- 判断用户当前是“信息查询”还是“文档写作/修订”
- 在写作场景下选择合适的 Skill
- 在对象不明确时做最小必要澄清
- 将结构化的写作意图交接给子 Agent
- 管理跨轮会话状态和最终结果回收

主 Agent 的关键特点有两点：

- 它偏“路由与决策”，而不是偏“执行”
- 它尽量避免介入写作期的事实加载、草稿来源判断和正文生成

这意味着主 Agent 关注的是：

- 要不要委派
- 委派给谁
- 当前轮次的结果如何回到主会话

而不是：

- 具体要读哪些模块事实
- 是否基于历史版本修订
- 正文应该怎么写

## 4.4 Skill 子 Agent

每个 Skill 在运行时会被实例化成一个子 Agent。子 Agent 是实际的写作执行者，负责：

- 根据当前 Skill 的 `SKILL.md` 作为写作规范
- 结合用户意图决定写作路径
- 判断是否需要读取当前草稿
- 判断是否需要加载历史正式版本
- 通过 MCP 工具加载模块事实、原型页面、Skill 资源
- 最终调用写作工具生成或修改正文

子 Agent 的本质是“按需创建的专业执行单元”。不同 Skill 可以拥有不同的 instruction、不同的参考资料和不同的执行侧重点，但共享统一的运行时工具协议。

## 4.5 Skill

Skill 是系统的专业能力封装单元，存放在 `skills/` 目录。一个 Skill 通常包含：

- `SKILL.md`：Skill 的定义、适用范围、写作规则、执行流程
- `references/`：参考结构、写作规则、检查清单等静态资料
- `templates/`：模板资源
- `scripts/`：可选的辅助脚本

Skill 的作用不是注册一堆硬编码逻辑，而是定义“某类文档应如何写”。系统通过加载 Skill 元信息和资源清单，让主 Agent 能选择 Skill，让子 Agent 能在执行时访问 Skill 私有上下文。

因此，Skill 是连接“通用 Agent 框架”和“具体文档专业方法”的关键层。

## 4.6 MCP Runtime / MCP Server

MCP Runtime 是系统的统一资源访问层。它把不同类型的运行时资源包装成稳定的命名空间工具，当前主要包括：

- `facts.*`：项目知识库中的模块事实
- `prototypes.*`：原型页面及其结构化页面事实
- `docs.*`：历史正式文档版本
- `artifacts.*`：工作区文件读写
- `skill.*`：当前 Skill 私有资源访问与脚本执行

其中要特别区分两类能力：

- 公共能力：`facts.*`、`prototypes.*`、`docs.*`、`artifacts.*`
- Skill 私有能力：`skill.*`

公共能力由统一的 MCP Runtime 注册，对主 Agent 和子 Agent 都可见。  
Skill 私有能力只在某个 Skill 子 Agent 执行时绑定到该 Skill 根目录，不能跨 Skill 越权访问。

这层的意义不只是“做工具封装”，更重要的是：

- 给不同 Agent 提供一致的资源访问方式
- 把资源访问语义从宿主代码里抽离出来
- 让系统具备向标准 remote MCP server 演进甚至独立暴露的能力

## 4.7 项目知识管理

项目知识管理位于 `project-facts/`，是整个系统的事实基础。它不是简单的文档堆，而是一套围绕模块聚合组织的知识管理模型，包括：

- `project-facts/modules/`：人工维护的模块档案
- `project-facts/generated/`：系统派生出的索引和聚合视图
- `project-facts/prototypes/`：原型整包及其解析输入

知识库的核心不是“把所有信息扁平放在一个总表”，而是“以模块为聚合根组织项目事实”。这一点是本项目非常关键的架构选择，后文会单独展开。

## 4.8 LLM

LLM 是整个系统的推理与生成引擎，当前通过统一配置管理支持：

- DeepSeek
- Qwen
- Ollama 兼容模型

系统通过 `llm_configs.json` 持久化模型配置，并通过适配层把配置转换为 LiteLLM/ADK 可用的运行参数。LLM 在系统中的角色主要有三类：

- 主 Agent 的意图理解、Skill 选择和回复生成
- 子 Agent 的写作推理与内容生成
- 个别摘要类任务，例如生成执行摘要或自动命名对话

从架构上看，LLM 是“核心引擎”，但不是“系统架构中心”。系统稳定性更多依赖于前面的资源组织、职责划分和上下文控制。

## 5. 这些组成部分之间的逻辑关系

## 5.1 静态关系

可以把核心组件之间的关系理解为：

```text
LLM 提供推理能力
  ^
  |
Agent（主/子）负责决策和执行
  ^
  |
MCP Runtime 提供统一资源访问协议
  ^
  |
项目知识库 / 历史文档 / Skill 资源 提供运行时上下文
```

再展开到本项目里，关系如下：

- 主 Agent 使用 LLM 做意图理解和编排决策
- 主 Agent 通过公共 MCP 工具做最小必要查询，或直接调用 `execute_skill`
- `execute_skill` 根据选中的 Skill 创建子 Agent
- 子 Agent 使用相同的公共 MCP 工具访问项目事实、原型和历史文档
- 子 Agent 额外获得当前 Skill 绑定的 `skill.*` 工具，用于读取参考资料、模板、脚本
- 子 Agent 使用写作工具生成正文，并把结果回传给主会话

## 5.2 运行时协作关系

### 场景一：信息查询

用户如果是在查询项目信息，例如：

- 有哪些模块
- 某模块有哪些功能
- 某模块对应哪些原型页面

主 Agent 会：

1. 判断这是查询型请求
2. 直接调用 `facts.*` 或 `prototypes.*`
3. 基于返回的事实结果直接答复

这个链路中通常不会创建子 Agent，因为不需要完整写作执行。

### 场景二：文档写作或修订

用户如果发起的是写作型请求，例如：

- 为某模块写用户手册
- 基于当前版本继续修改设计文档

主 Agent 会：

1. 判断是写作型请求
2. 识别目标对象和文档类型
3. 选择合适 Skill
4. 提炼 `user_intent`
5. 调用 `execute_skill`

随后子 Agent 会：

1. 接收主 Agent 交接的上下文摘要和写作任务
2. 决定是否读取当前草稿
3. 决定是否读取历史正式版本
4. 决定是否加载模块事实、原型页面、Skill 参考资源
5. 调用写作工具生成草稿或修订正文
6. 输出执行总结，并将产物状态同步回主会话

## 6. 关键运行链路

## 6.1 从用户请求到主 Agent

用户请求首先进入前端对话界面，然后通过 REST 或 WebSocket 发给后端。后端创建或复用会话上下文，再调用 Agent 运行入口。

这一层做的不是内容推理，而是：

- 会话绑定
- 流式消息通道建立
- 当前轮次上下文初始化
- 执行事件与状态收集

## 6.2 主 Agent 的最小编排闭环

主 Agent 的工作闭环是：

1. 识别意图
2. 决定是直接回答还是委派 Skill
3. 必要时做最小澄清
4. 回收子 Agent 结果并结束本轮

主 Agent 不负责拉满上下文，不负责深入执行，也不负责最终正文撰写。它是整个系统的“任务入口与路由层”。

## 6.3 子 Agent 的写作闭环

子 Agent 的写作闭环是：

1. 理解 Skill 规范
2. 读取必要事实
3. 判断草稿来源
4. 判断历史版本来源
5. 读取 Skill 参考资料
6. 调用写作工具输出正文
7. 输出本轮写作完成总结

这意味着写作期所有真正消耗上下文窗口、需要连续推理的动作，都被收敛到子 Agent 内部完成。

## 6.4 文档保存闭环

当对话中的草稿需要正式落盘时，系统会调用文档版本服务，将文档保存到 `doc_output/` 下的版本化目录中。正式文档与会话草稿分离管理：

- 会话草稿属于对话态
- 正式版本属于项目产物态

这种分离让“正在写什么”和“已经发布什么”有清晰边界。

## 7. 项目知识管理设计思路

## 7.1 为什么要以模块为聚合根

本项目没有把知识库建设成一个完全细粒度、强结构化、到处可独立查询的知识图谱，而是采用“模块档案作为唯一人工维护单元”的思路。原因主要有四点：

### 1. 更符合人工维护习惯

实际项目中，产品、研发、实施更容易围绕“一个模块”补充信息，而不是分别维护：

- 一张 API 总表
- 一张页面总表
- 一张类关系总表
- 一张依赖关系总表

模块是业务和工程都能理解的天然边界。

### 2. 降低事实源分裂风险

如果不同维度信息分散在多个独立事实源中，就会出现：

- 用户不知道改哪一份
- 同一事实多处重复维护
- Agent 读取时很难判断哪份是权威来源

模块档案把功能描述、功能点、API、页面、包类、依赖关系聚合到同一份档案中，降低了事实漂移。

### 3. 更适合 Agent 加载最小闭环上下文

对于写作型任务，Agent 通常并不需要先拿到整个项目的全量细粒度知识，它更需要的是：

- 某个目标模块的完整事实包

`facts.get_module(module_ref)` 恰好对应这种真实使用路径。Agent 拿到模块聚合根后，已经可以完成很多写作任务；只有在需要页面细节时，再进一步加载原型页面。

### 4. 让系统派生层可以稳定生成

人工维护层只维护模块档案，系统再自动派生：

- 模块索引
- 模块 ID 映射
- 关系索引
- 模块浏览视图

这种“人工维护层 + 系统派生层”分离，既保留了维护友好性，也让检索和展示具备结构化能力。

## 7.2 知识管理的分层

项目知识库实际上分为两层：

### 人工维护层

- 目录：`project-facts/modules/*.md`
- 特点：面向人编辑、自然语言优先、允许不完整

### 系统派生层

- 目录：`project-facts/generated/*`
- 特点：面向检索、加载、展示、引用解析

这两层分离的价值在于：

- 人工维护不被机器结构绑死
- Agent 和前端又能获得稳定结构

## 7.3 为什么 facts 工具只围绕模块聚合根展开

当前 `facts.*` 第一阶段只保留两个最核心工具：

- `facts.list_modules()`
- `facts.get_module(module_ref)`

这是一个有意收敛的设计，而不是能力不够。它体现的判断是：

- 当前最稳定的维护单元是模块
- 当前最真实的查询主路径也是模块清单和模块主档
- 过早暴露大量细粒度 facts 工具，会让模型在工具选择和参数推理上更混乱

换句话说，本项目当前的知识管理重点不是“最大化工具数量”，而是“保证最关键路径简单且稳定”。

## 8. 主子 Agent 隔离设计思路

## 8.1 设计目标

主子 Agent 分层的核心目标，是同时解决以下问题：

- 上下文窗口容易膨胀
- 编排职责和执行职责容易混在一起
- 不同 Skill 的专业规范容易互相污染
- 写作过程中的事实加载返回值过多，会污染主会话

## 8.2 主 Agent 为什么不能承担完整写作

如果让主 Agent 同时负责：

- 意图识别
- Skill 选择
- 草稿来源判断
- 历史文档选择
- 模块事实加载
- 原型页面查询
- Skill 参考资料读取
- 最终正文写作

那么会出现几个问题：

- 主 Agent 的提示词和工具面会急剧膨胀
- 多轮对话中，大量事实加载结果会进入主会话上下文
- 每个 Skill 的专业规则都要挤进同一个编排 Agent
- 写作期和编排期的思考混在一起，难以稳定控制

因此，主 Agent 必须收缩职责。

## 8.3 子 Agent 隔离如何解决上下文问题

当前方案的关键不是“完全断开主子 Agent”，而是“按最小交接原则隔离上下文”。

主 Agent 交给子 Agent 的不是完整运行历史，而是：

- 当前轮次的结构化写作意图
- 当前草稿和目标对象的稳定信号
- 上次执行摘要
- 必要的澄清结论

子 Agent 自己维护本轮执行时的工作上下文，包括：

- 本轮加载的模块事实
- 本轮读取的历史文档
- 本轮读取的 Skill 资源
- 本轮推理过程和工具调用过程

这样做的好处是：

- 主会话不会被大段事实加载内容污染
- 子 Agent 可以针对当前写作任务自由构造执行上下文
- 执行期上下文在任务结束后自然收敛

## 8.4 独立 session 的意义

Skill 子 Agent 在执行时使用独立 session，其内部 ReAct 历史不直接写入主 Agent session。这样做的核心收益有三点：

### 1. 控制 token 膨胀

写作过程中会出现大量：

- 工具调用记录
- 事实文本
- 页面事实
- 中间推理

如果这些都进入主会话，后续每一轮主 Agent 都要背负这些历史。

### 2. 保持主会话干净

主会话只保留必要结果，例如：

- 本轮是否产生草稿
- 本轮选中了哪个 Skill
- 本轮执行摘要是什么

主会话因此更适合作为长期对话记忆容器。

### 3. 让 Skill 成为真正可替换的执行单元

子 Agent 是按 Skill 动态构建的。如果它们共用主 Agent 的完整执行历史，不同 Skill 的执行痕迹会互相干扰。独立 session 有助于把 Skill 执行变成一个边界清晰的“任务沙箱”。

## 8.5 为什么不是完全隔离

主子 Agent 不是完全无关的两个世界。系统仍然保留一部分共享状态，例如：

- 当前会话是否已有草稿
- 当前目标模块
- 当前系统/子系统信息
- 上次写作执行摘要
- 用户澄清结论

原因是写作任务本质上仍属于同一场多轮对话。完全隔离会让子 Agent 无法延续前文，完全共享又会导致上下文失控。因此当前方案采用的是：

- 主会话级稳定状态共享
- 子执行级工作上下文隔离

这是一种折中但非常实用的架构选择。

## 9. MCP server 在整体架构中的位置

MCP Runtime 在本项目中既是内部统一访问层，也被设计成可独立暴露的 MCP server。它在整体架构中的位置可以概括为：

- 对上：向主 Agent 和子 Agent 暴露统一工具能力面
- 对下：适配项目事实库、历史文档服务、原型解析结果和本地文件系统

它不负责：

- Skill 选择
- 子 Agent 生命周期管理
- 会话编排
- 正文写作

它负责的是：

- 把不同资源域转换成清晰、稳定、可审计的工具协议

因此它是“资源访问层”，不是“编排层”。

## 10. LLM 在整体架构中的位置

LLM 在本系统中并不是一个孤立的大模型调用点，而是通过两类 Agent 角色被组织起来：

- 主 Agent 使用 LLM 做编排判断
- 子 Agent 使用 LLM 做执行推理和内容生成

同时，系统通过统一配置层实现：

- 多 provider 支持
- OpenAI 兼容接口适配
- 参数归一
- 推理模式控制

这意味着 LLM 可以替换，但系统结构不需要随之重做。项目的核心可持续性并不依赖某一个模型，而依赖：

- 事实组织是否稳定
- 资源访问协议是否统一
- Agent 职责边界是否清晰

## 12. 关键设计决策总结

本项目当前最重要的架构决策可以概括为以下五点：

### 决策一：以模块为聚合根组织项目知识

这是知识管理层的核心决策。模块档案是唯一人工维护单元，其他索引和视图由系统自动派生。

### 决策二：主 Agent 只做编排，不做完整写作

主 Agent 负责理解用户需求、选择 Skill、发起委派和回收结果，避免承担写作执行链路。

### 决策三：Skill 子 Agent 负责写作期决策与执行

包括草稿来源判断、历史版本选择、事实加载顺序、Skill 参考资料读取和正文生成。

### 决策四：通过 MCP Runtime 统一运行时资源访问

把项目事实、原型、历史文档、工作区文件、Skill 私有资源都收敛到统一的工具协议下，但保留不同资源域的语义边界。

### 决策五：主子 Agent 隔离以控制上下文和职责边界

主会话保留稳定记忆，子执行保留工作上下文，避免长对话下的上下文污染和工具历史膨胀。

## 13. 一句话总结

NextAgent Doc Assistant 的整体架构可以概括为：

以“模块聚合的项目知识库”作为事实底座，以“主 Agent 编排 + Skill 子 Agent 执行”作为智能体骨架，以 MCP Runtime 作为统一资源访问层，以 LLM 作为推理引擎，共同构成一个面向软件工程文档生产的可扩展 Agent 系统。
